# 新版 PRD 导入流程（导入 → 检查 → 审核 → 提醒 → 修改 → 验证）

负责人定期投放以日期命名的新版 PRD 文件夹（如 `docs/prd/PRD-20260903/`）。本流程为 2026-09-03 拍板、09-04 实跑验证的固定流程。**核心铁律：新版未确认前不动工改造；md ↔ 原型矛盾不自行取舍；删除旧版仅在全部冲突点确认之后。**

## 阶段一：增量核对（检查）

目标：核实新版是否为**纯增量**（只新增、不改已有内容）；改动/删除既有内容一律算冲突点。

1. **文件级盘点**：`diff -rq 旧版 新版`，分类为 逐字节相同 / 改写 / 新增 / 移除 / 卫生项（.DS_Store、.obsidian、.bak 等）。空目录、悬空引用（md 里引的图不存在）也要查。
2. **语义级对比**（改写项逐个做，量大时按模块分组派并行只读 agent）：
   - **md 文档**：新旧逐节对比，区分「纯新增章节」与「既有条款被改写/删除/口径反转」，冲突点引双方原文+定位。
   - **交互原型 html**：两版**各取最终覆写生效态**（多层 patch，后定义覆盖先定义——先 grep render 函数清单，再确认末尾覆写层）再互比；新增模块/render=增量，既有模块内容变动=冲突。逐字节比对无意义，必须语义级。
   - **各模块必填选填字段一览表**：按模块逐行对比。
   - 新增独立文档（规范类）：通读摘要，并**交叉核对它与既有各模块 md 是否口径冲突**（新规范可能与未同步的旧条款矛盾）。
3. **产出对比分析文件** `docs/prd/<旧版名>→<新版名>-对比分析.md`，结构：
   - 〇 总体结论 + 结构级差异表（含定性：冲突/增量/卫生项/缺陷/忽略）
   - 一 冲突点表（分组编号，列：位置｜旧版原文｜新版原文｜变更性质）
   - 二 增量清单（摘要即可）
   - 三 与 demo 既有拍板的关系（新版吸收了哪些已实现口径=利好；反转了哪些近期拍板=单列提醒）
   - 四 待确认清单：给负责人**建议裁决方式**——格式/措辞级与已实现一致项建议批量确认；**新版内部自相矛盾项（md 说一套、原型说另一套）单列**，因为"以新版为准"无法自动裁决，必须二选一。
4. 对比分析文件 commit + push，向负责人汇报要点并等待裁决。

## 阶段二：审核与闭环（负责人确认）

1. 负责人逐项/批量裁决（历史经验：多为「完全以新版为准」+ 若干项「先记录不改造」）。
2. 负责人若在对比分析文件上直接标注：先把**标注版 commit 存档**再删（git 历史兜底）。
3. 结构级裁决即时落地（保留目录用 .gitkeep 占位、删冗余文件等）。
4. **建问题记录** `docs/PRD-review/PRD-<日期>-问题记录.md`：挂账项（冻结不改造的）逐条 Q 编号，写明双方依据与「demo 保持现状待拍板」。
5. 全部冲突确认后：**删除旧版 PRD 文件夹与对比分析文件**（git 可溯），docs/prd/ 收敛为单版本。
6. 当日 `docs/PRD-review/YYYY-MM-DD.md` 记录第一步闭环与裁决（三段式，见 daily-update-log skill）。

## 阶段三：改造（修改）

1. **冻结区先行明确**：挂账 Q 对应的能力/组件列成禁改清单，写进每个实施 agent 的任务书。
2. 按模块分组派并行实施 agent，任务书要素：权威基准（新版 md + 原型最终覆写态，先通读再动手）、冻结区、共享文件所有权（同一共享组件只归一组改，其余组传参消费；有依赖的组串行）、既有约定（标准件复用、mock 模式 `xxxMock.js`+USE_MOCK 分流、文案照 md/原型逐字、密钥 secretMask、测试重写注明对齐日期）、禁止事项（git/pkill/dev server/改 docs 归主流程）。
3. 每组输出：实施摘要（逐条 done/skip+原因）+ **新发现问题**（尤其新版 md↔原型不一致——默认按 md 落地并记录）。
4. 新发现问题追加进问题记录（续 Q 编号，注明已按哪方落地）。

## 阶段四：验证与提交

1. 全量 `npx vitest run` 必须全绿；`vite build` 通过。
2. 关键改动页面 Playwright 冒烟（页面渲染、探针文案、console/pageerror 零错误）。
3. 复核冻结区确实未动。
4. 当日 PRD-review 记录改造轮（三段式+影响面）；git commit + push（工程经 GitHub 协作，开工前先 pull）。
5. **提醒负责人**：确认问题记录——纯确认项标【已解决】；裁决可能派生新改造（挂账项解冻）；属 PRD 文档缺陷的提醒转 PRD 团队回改 md/原型，否则下次导入会重复核出。全部问题解决后问题记录**文件名**标【已解决】（git mv）。

## 硬约束速查

- 原型以**最终覆写生效态**为准；模块目录截图仅参考不作依据。
- 冲突点性质判断保守：不确定算冲突。宁全勿漏，微小文案差异也收。
- 「以新版为准」不能自动裁决新版内部矛盾——这类必须单独提请负责人二选一。
- 推翻近期拍板的条目必须显式提醒（列明是哪次拍板）。
- 改造中对 md↔原型矛盾的默认取向：**按 md 落地 + 记录**（除非任务书另有指示）。
