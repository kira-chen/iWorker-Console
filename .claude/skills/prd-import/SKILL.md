# 新版 PRD 导入流程（2026-09-07 负责人改版）

负责人定期投放以日期命名的新版 PRD 文件夹（如 `docs/prd/PRD-20260904/`）。本流程为 2026-09-03 拍板、09-04 实跑、09-06/07 按负责人指示改版的固定流程。

**触发铁律（2026-09-06 负责人纠偏后的硬规则）**：发现 `docs/prd/` 下出现新日期文件夹时，**只做「报告发现 + 询问是否启动」，不自动启动本流程**；负责人本地未入库的新文件夹**绝不擅自 commit/push**。其余铁律：新版未确认前不动工改造；md ↔ 原型矛盾不自行取舍；删除旧版仅在冲突点确认之后。

> **适用性说明（2026-09-04 负责人确认）**：原型相关环节（最终覆写态提取、md↔原型一致性审查、截图并排比对）**仅当该版本包含 HTML 原型文件时适用**。按负责人预告，HTML 原型将逐步退场、团队转为直接在代码层面改造——届时对齐基准以 md + 代码现状为准，基准口径由负责人另行拍板后更新本技能。

## 阶段一：版本变动审查 → 01-改动记录

目标：核实新版较上一版改了什么；改动/删除既有内容一律算冲突点。

1. **文件级盘点**：`diff -rq 旧版 新版`，分类为 逐字节相同 / 改写 / 新增 / 移除 / 卫生项（.DS_Store、.obsidian、.bak 等）。空目录、悬空引用（md 里引的图不存在）也要查。
2. **语义级对比**（改写项逐个做，量大时按模块分组派并行只读 agent）：
   - **md 文档**：新旧逐节对比，区分「纯新增章节」与「既有条款被改写/删除/口径反转」，冲突点引双方原文+定位。
   - **交互原型 html**：两版**各取最终覆写生效态**（多层 patch，后定义覆盖先定义——先 grep render 函数清单，再确认末尾覆写层）再互比。逐字节比对无意义，必须语义级。
   - **各模块必填选填字段一览表**：按模块逐行对比。
   - 新增独立文档（规范类）：通读摘要，并交叉核对它与既有各模块 md 是否口径冲突。
3. **产出改动记录文件** `docs/01-新版本PRD改动记录/改动记录-<新版日期YYYYMMDD>.md`（**永久留档，不再事后删除**），结构：
   - 头部：总体结论（纯增量/定点修订/大改版）+ 结构级差异表（含定性：冲突/增量/卫生项/缺陷）；
   - 正文：**每个变动主题一节，三段式**（同 PRD-review 日记录格式）——「需求/问题」=新版改了什么、「方案」=新旧口径对比要点与依据定位、「影响面」=涉及哪些已实现代码/文档/既往拍板；
   - 末尾：**待确认清单**——需负责人拍板的版本间冲突逐条编号；格式/措辞级与已实现一致项建议批量确认；**新版内部自相矛盾项单列**（"以新版为准"无法自动裁决，必须二选一）；**推翻近期拍板的复发项显式提醒**（列明是哪次拍板）。
4. 本地 commit（**不主动 push**，推送按负责人指示），向负责人汇报要点。

## 阶段二：全量 md↔原型一致性审查 → 02-审查结果

目标：对新版整包做 md 文字稿 ↔ 交互原型 html 的全量一致性体检（含一览表、规范类根文档），不只看增量。

1. **方法（2026-09-06 实跑口径）**：按模块分组派并行只读审查 agent（参考分组：岗位系 / 知识库 / 连接器三件套 / 专家·技能·模型 / 治理域 / 组织域+根文档交叉核对）；原型以**最终覆写生效态**为准；每条发现**回查上一版**判定是否旧版遗留。
2. **产出审查结果文件** `docs/02-PRD和原型一致性审查/PRD与原型一致性审查结果-<新版日期YYYYMMDD>.md`，模板（以 20260904 版为样板）：
   - 头部：审查基准与来源说明、**标识说明**（旧版遗留条目标题带【<上一版日期>已存在】，无标识 = 本版新引入，头部列明新引入 Q 号清单）、分类总表；
   - 正文：**Q 编号条目按七类聚合分章**（章序 = 建议处理顺序，每章开头写处理方式）——A 口径矛盾（需选边）/ C 原型未跟进 md（默认以 md 为准）/ B 文案措辞微差（整类批量）/ E 原型超出 md（补文档或删功能）/ F PRD 文档自身缺陷（纯 md 修订）/ D 原型工程质量（修原型）/ G 演示数据与资产；条目格式 `## Qn.【…已存在】模块·差异标题` + 差异描述 + md/原型依据 + 原编号；
   - 附录：各路审查组的**审查覆盖说明**（核对范围/覆写层判定/上一版对照方法/未覆盖区域）。
3. 本文件**只列差异点，不含处理决策**；本地 commit，交负责人转产品经理按类修复。

## 阶段三：负责人审核与版本切换

1. 负责人在**两份文件上直接批注决策**（不再另建问题记录台账）：版本间冲突批在 01-改动记录的待确认清单；md↔原型差异批在 02-审查结果对应条目。销项后条目标题加【已解决】。
2. 负责人批注后按标记执行：代码类落地并回归、移交产品类汇总转交、"采纳现状"类直接销项。
3. 结构级裁决即时落地（保留目录 .gitkeep 占位、删冗余文件等）。
4. 版本间冲突全部确认后执行**版本切换**：删除旧版 PRD 文件夹（git 可溯），新版入库，docs/prd/ 收敛为单版本。
5. 当日 `docs/PRD-review/YYYY-MM-DD.md` 记录闭环与裁决（三段式，见 daily-update-log skill）。

## 阶段四：改造（负责人拍板后启动，不自动进入）

1. **冻结区先行明确**：挂账条目对应的能力/组件列成禁改清单，写进每个实施 agent 的任务书。
2. 按模块分组派并行实施 agent，任务书要素：权威基准（新版 md + 原型最终覆写态，先通读再动手）、**原型骨架提取（2026-09-04 拍板：从原型提取目标模块的 DOM 结构与 CSS 骨架——卡片分区/内容列宽与居中/区块头构成/hint 位置/输入占位——照结构实现，视觉细节再用站内令牌映射；只搬字段清单不搬骨架视为未完成）**、冻结区、共享文件所有权（同一共享组件只归一组改，其余组传参消费；有依赖的组串行）、既有约定（标准件复用、mock 模式 `xxxMock.js`+USE_MOCK 分流、mock 持久化 persist()/改种子 bump version、文案照 md/原型逐字、密钥 secretMask、测试重写注明对齐日期）、禁止事项（git/pkill/dev server/改 docs 归主流程）。
3. 每组输出：实施摘要（逐条 done/skip+原因）+ 新发现问题（默认按 md 落地并记录，追加进 02-审查结果续 Q 编号）。

## 阶段五：验证与提交

1. 全量 `npx vitest run` 必须全绿；`vite build` 通过。
2. 关键改动页面 Playwright 冒烟（页面渲染、探针文案、console/pageerror 零错误）。
3. **视觉比对（2026-09-04 拍板）**：改动页面必须 Playwright 截图与原型**并排逐区块比对**——布局容器（居中/限宽/底色）、卡片分区与区块头、hint 与占位、输入框编辑态是否白底可输入（只读逻辑泄漏高频回归点）；**测试全绿不构成视觉达标**，主流程收货须亲自看截图。
4. 复核冻结区确实未动。
5. 当日 PRD-review 记录改造轮（三段式+影响面）；本地 commit（**不主动 push**，推送按负责人指示；开工前先 pull）。
6. **提醒负责人**：两份文件的开放条目待销项；属 PRD 文档缺陷的提醒转 PRD 团队回改 md/原型，否则下次导入会重复核出。

## 硬约束速查

- 发现新 PRD 文件夹：**先报告 + 询问，不自动启动**；不擅自 commit 负责人未入库的材料；全程**不主动 push**。
- 原型以**最终覆写生效态**为准；模块目录截图仅参考不作依据。
- 冲突点性质判断保守：不确定算冲突。宁全勿漏，微小文案差异也收。
- 「以新版为准」不能自动裁决新版内部矛盾——这类必须单独提请负责人二选一。
- 推翻近期拍板的条目（复发项）必须显式提醒（列明是哪次拍板）。
- 改造中对 md↔原型矛盾的默认取向：**按 md 落地 + 记录**（除非任务书另有指示）。
- 决策承载：负责人批注在 01-改动记录 / 02-审查结果 两份文件上，销项标【已解决】；不再建独立问题记录台账。
- `docs/03-PRD和原型待决策差异点/` 为负责人预留目录，暂不启用，勿写入。
- 本技能的任何更新须先提请负责人确认，不得直接改。
