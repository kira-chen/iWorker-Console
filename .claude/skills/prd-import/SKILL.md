# PRD 修订处理流程（2026-09-17 负责人三次改版：接入基线表 / 同批改模式 / PR 流程 / 待办文件夹）

**模式**：`docs/PRD/数字员工管理端PRD/` 是 PRD **长期正本**——修订直接改 md 并提交，**git diff 即变更记录**。**md 为唯一口径**（原型已退场；PRD 交付不含截图，核对直接对照 md 文字与源码运行效果）。

**触发铁律**：发现 PRD md 有 git 变更时，**只做「报告发现 + 询问是否启动」，不自动启动本流程**；负责人本地未提交的 PRD 改动**绝不擅自 commit/push**。修订确认前不动工改造。

> **多人协同前置（每次动工前）**：`git pull` 拉齐远端；若远端有他人新提交，先合并跑绿再开工；他人正在改的文件不并行硬改（并行/高风险批次用隔离 git worktree）。

## 阶段零：确定范围与模式

1. **基线**：读仓库根 `README.md`「基线表」的「`/prd-import` 上轮终点」commit（**唯一落点**，不看任何产出文件尾部）。变更范围 = `git diff <基线>..HEAD -- docs/PRD/` + `git log`，列出全部 md 变更（含新增/删除/改名）。
2. **模式判定**（`git log` 核每条 PRD 变更 commit 是否同时含 `frontend/` 改动、作者是谁）：
   - **同批改**：PRD 与代码出自同一人同一批 commit（典型：浦月改需求时一并改页面）。**跳过阶段一**——改动者即产品口径，不需要待确认清单；直接进阶段二，**审查结果由改动者本人出具并对其负责**（2026-09-17 负责人定：不设第三方核）。若由他人代跑本技能，产出仍署改动者为责任人，并把「请确认」条目记进改动者的待办文件。
   - **分批改**：PRD 先改、代码未动（外部送来的修订或负责人直改 md）。走完整阶段一～五。
3. 向负责人报：基线、变更清单、判定的模式，等确认后进入下一阶段。

## 阶段一：变更审查 → 01-改动记录（仅分批改模式）

目标：核实本批修订改了什么；改动/删除既有条款一律算冲突点。

1. **语义级审查**（变更文件逐个做，量大时按模块分组派并行只读 agent）：diff 逐块读，区分「纯新增章节」与「既有条款被改写/删除/口径反转」，冲突点引新旧原文 + 定位（旧文 `git show <基线>:路径`）；《各模块必填选填字段一览表》有变更时按模块逐行对比；新增规范类文档通读并交叉核对与各模块 md 是否冲突。
2. **产出** `docs/01-PRD改动记录/改动记录-<YYYYMMDD>.md`（目录不存在则新建；同日多批加 -2）：
   - **文件头四行**（工作项强制）：`状态：进行中 / 责任人 / 闭环条件：待确认清单全部销项 / 关联：基线 commit`；
   - 头部：总体结论 + 变更文件清单表（定性：冲突/增量/卫生项/缺陷）+ 本批基线与终点 commit；
   - 正文：每个变动主题一节，三段式「需求/问题 → 方案 → 影响面」；
   - 末尾：**待确认清单**——需负责人拍板的冲突逐条编号；措辞级与已实现一致项建议批量确认；**修订内部自相矛盾项单列**（必须二选一）；**推翻近期拍板的复发项显式提醒**（列明是哪次拍板）。
3. 本地 commit（显式路径），向负责人汇报要点。

## 阶段二：md↔代码一致性审查 → 02-审查结果

目标：对修订后的 PRD 做 **md 文字稿 ↔ 代码现状**的一致性体检（同批改模式默认只审变更模块；分批改模式默认全量，含一览表与规范类根文档；范围可经负责人同意调整）。

1. **方法**：按模块分组派并行只读 agent（岗位系 / 知识库 / 连接器三件套 / 专家·技能·模型 / 治理域 / 组织域 + 根文档）；代码侧以**页面实际渲染 + mock 数据层语义**为准（必要时起 dev 用 Playwright 实走取证，勿只读模板下结论）；每条发现回查基线版 md 与近期拍板判定是「本批改口径」「旧有遗留」还是「代码实现缺陷」。**盘点以实数为准，勿采信旧审计里的数字与归因**。
2. **产出** `docs/02-PRD与代码一致性审查/PRD与代码现状一致性审查结果-<YYYYMMDD>.md`：
   - **文件头四行**：`状态：进行中 / 责任人：<改动者或本轮执行人> / 闭环条件：每条 Q 标已解决或不做 / 关联：基线 commit、01 记录（若有）`；
   - 头部：审查基准（PRD 终点 commit）、标识说明（旧有遗留条目标【<上批日期>已存在】）、分类总表；
   - 正文：**Q 编号条目按类聚合分章**——A 口径矛盾 / C 代码未跟进 md（默认按 md 落地）/ B 文案微差（整类批量）/ E 代码超出 md（补文档或删功能）/ F PRD 自身缺陷（可直接改 md 提交，列明供确认）/ G 演示数据与资产；条目格式 `## Qn.【…已存在】模块·差异标题` + 差异描述 + md/代码依据（file:line）；
   - 附录：各路审查组的**审查覆盖说明**。
3. 本文件**只列差异点，不含处理决策**；本地 commit，交负责人裁决。

## 阶段三：负责人审核

1. 负责人在 01（若有）/ 02 两份文件上**直接批注决策**，销项后条目标题加【已解决】。等负责人裁决的整份清单若需集中，放 `docs/03-待决策清单/`。
2. 按批注执行：代码类落地并回归、纯 md 修订类直接改 PRD 正本提交、「采纳现状」类 md 回改并在条目注明。
3. **需要他人处理的条目**（按模块分派：01 总览 / 02 岗位 / 03 能力 / 05 治理 / 06 组织 → 浦月 `yuepu`；04 运行 → 曹春林 `clcao`）追加到 `docs/产品经理待办任务/<人>.md`「待处理」表（序号 / 未处理 / 发起人 / 详述：现状·依据·期望），**不在审查文件里等人看**。
4. 裁决留痕：写进 02 条目本身与 commit message；不写日记录（PRD-review 已停用）。

## 阶段四：改造（负责人拍板后启动，不自动进入）

1. **取舍以工程大原则为评判基准**（根 CLAUDE.md）：①完整表达产品设计想法 ②代码示例让研发易读懂；两者都不沾的投入默认不做。
2. **冻结区先行明确**：挂账条目对应的能力/组件列成禁改清单，写进每个实施 agent 的任务书。
3. **方案先行**：改动面大或涉共享层时，先派架构师做实地盘点与方案设计；方案稿**只有负责人明确指令才建** `docs/调研讨论/YYYY-MM-DD-主题.md`（三条铁规见 `docs/README.md`），否则写进 02 条目或 commit message。
4. 按模块分组派并行实施 agent，任务书要素：权威基准（相应模块 md，先通读再动手）、视觉骨架基准（站内既有页面范式 + 设计令牌；`docs/规范/UI/` 设计图仅视觉参考）、冻结区、共享文件所有权（同一共享组件只归一组改；有依赖的组串行；高风险组走隔离 worktree）、既有约定（标准件复用、mock `xxxMock.js` + USE_MOCK 分流、mock 持久化 persist() / 改种子 bump version、文案照 md 逐字、密钥 secretMask、测试头注写对齐日期与 md 章节）、禁止事项（git 写命令 / pkill / 改 docs 归主流程；dev server 各组独立端口）。
5. 每组输出：实施摘要（逐条 done/skip + 原因）+ 新发现问题（默认按 md 落地并记录，追加进 02 续 Q 编号）；**每个验证过的闭环批次由主流程复核后独立 commit**（全量测试绿 + build 通过才提，显式路径；一件事一条）。

## 阶段五：验证、闭环与 PR

1. 全量 `npm run test` 全绿；`npm run build` 通过。**CI 跑 Node 22**（本机可能更高）：本地绿 CI 红时以 CI 为准，先查 Node 差异（见 `.github/workflows/ci.yml` 注释）。
2. 关键改动页面 Playwright 冒烟（渲染、探针文案、console/pageerror 零错误）。
3. **视觉验证**：改动页面截图与改动前基线及站内同类页面比对——布局容器、卡片分区、hint 与占位、双主题、输入框编辑态；**测试全绿不构成视觉达标**，主流程亲自看截图；改动大的批次加多角色验收。
4. 复核冻结区确实未动。
5. **闭环**：01/02 文件每条有结论 → 文件头状态改「已闭环（日期）」→ **改仓库根 README 基线表**「`/prd-import` 上轮终点」为本批终点 commit（同一 commit）。归档（`git rm` + 本机 Archive/）只由负责人做，提醒即可。
6. **推送走 PR**（CLAUDE.md「PR 流程与 CI」）：分支创建与 push 仍**按负责人指令**——`git switch -c <类型>/<简述>` → 攒够一个闭环批次 `git push -u origin <分支>` → 开 PR、Enable auto-merge → CI 绿自动合入。推前门禁：fetch 无分叉（有分叉先 merge、跑绿）、全量测试绿、build 过、无密钥、无误收临时文件。不直推 main。
7. 向负责人报：远端点位、基线表已推进、待办文件里给他人的条目。

## 硬约束速查

- 发现 PRD md 变更：**先报告 + 询问，不自动启动**；不擅自 commit 负责人未提交的 PRD 改动；push / 开分支仅按负责人指令，且只走 PR。
- **`docs/PRD/数字员工管理端PRD/` 长期正本、md 唯一口径**；不建日期版本文件夹；PRD 不含截图。
- 变更范围以 **README 基线表**为起点；闭环时推进基线表。
- 模式判定在前：同批改跳过阶段一，作者对自己的产物负责。
- 每次动工前先 `git pull`；他人在改的文件不并行硬改。
- 冲突点性质判断保守：不确定算冲突。修订内部自相矛盾必须提请负责人二选一；推翻近期拍板的复发项必须显式提醒。
- 改造中 md↔代码矛盾的默认取向：**按 md 落地 + 记录**；md 与既往拍板冲突的例外——停下提请裁决。
- 决策承载：负责人批注在 01 / 02 文件上；跨人待办进 `产品经理待办任务/`；不写日记录、不另建台账。
- 工作项文件头四行强制；`docs/` 下新建目录须先说明用途与业务流关系并经确认。
- 本技能的任何更新须先提请负责人确认（本版 = 负责人 2026-09-17 批准的修订稿 7.3 + 当日新增机制）。
