# PRD 修订处理流程（2026-09-10 负责人二次改版：git 直改模式）

**模式（2026-09-10 负责人拍板）**：`docs/PRD/数字员工管理端PRD/` 是 PRD **长期正本**——修订直接改其中的 md 并提交，**git diff 即变更记录**；不再投放日期文件夹整包替换（旧整包导入流程存 git 历史 2026-09-10 上午版，万一再收到外部整包，先向负责人确认后按旧流程兜底）。**md 为唯一口径**（原型已退场：不再修改、不再附带；旧原型与模块截图仅历史参考）。

**触发铁律**：发现 PRD md 有 git 变更（本地 pull 到他人提交、或负责人知会「PRD 更新了」）时，**只做「报告发现 + 询问是否启动」，不自动启动本流程**；负责人本地未提交的 PRD 改动**绝不擅自 commit/push**。修订确认前不动工改造。

> **多人协同前置（每次动工前）**：`git pull` 拉齐远端（origin 走 HTTPS）；若远端有他人新提交，先合并跑绿再开工；他人正在改的文件不并行硬改。**并行/高风险批次用隔离 git worktree**（主工作区与 worktree 改动落点物理隔离，验收后由主流程取 diff 合并）。

## 阶段一：变更审查 → 01-改动记录

目标：核实本批修订改了什么；改动/删除既有条款一律算冲突点。

1. **确定变更范围（git 直改模式的核心）**：以**上一轮已闭环的 PRD 基线 commit**（查上一份 01-改动记录尾部记载，或 `git log -- docs/PRD/` 找上次处理到的点）为起点，`git diff <基线>..HEAD -- docs/PRD/` + `git log` 列出本批全部 md 变更（含新增/删除/改名文件与图片资产）。
2. **语义级审查**（变更文件逐个做，量大时按模块分组派并行只读 agent）：
   - **md 文档**：diff 逐块读，区分「纯新增章节」与「既有条款被改写/删除/口径反转」，冲突点引新旧原文+定位（git 侧旧文用 `git show <基线>:路径` 取）。
   - **各模块必填选填字段一览表**：有变更时按模块逐行对比。
   - 新增独立文档（规范类）：通读摘要，并交叉核对与既有各模块 md 是否口径冲突。
3. **产出改动记录文件** `docs/01-PRD改动记录/改动记录-<修订批次日期YYYYMMDD>.md`（**永久留档**；同日多批加后缀 -2），结构：
   - 头部：总体结论（纯增量/定点修订/大改版）+ 变更文件清单表（含定性：冲突/增量/卫生项/缺陷）+ **本批基线与终点 commit 号**（下一轮以终点为新基线）；
   - 正文：**每个变动主题一节，三段式**（同 PRD-review 日记录格式）——「需求/问题」=本批改了什么、「方案」=新旧口径对比要点与依据定位、「影响面」=涉及哪些已实现代码/文档/既往拍板；
   - 末尾：**待确认清单**——需负责人拍板的冲突逐条编号；措辞级与已实现一致项建议批量确认；**修订内部自相矛盾项单列**（必须二选一）；**推翻近期拍板的复发项显式提醒**（列明是哪次拍板）。
4. 本地 commit（显式路径；**不主动 push**），向负责人汇报要点。

## 阶段二：全量 md↔代码现状一致性审查 → 02-审查结果

目标：对修订后的 PRD 整包做 **md 文字稿 ↔ 代码现状**的全量一致性体检（含一览表、规范类根文档），不只看增量——「现状」的唯一载体就是代码与页面实际表现。定点小修订经负责人同意可降级为「仅变更模块」范围。

1. **方法**：按模块分组派并行只读审查 agent（参考分组：岗位系 / 知识库 / 连接器三件套 / 专家·技能·模型 / 治理域 / 组织域+根文档交叉核对）；代码侧以**页面实际渲染 + mock 数据层语义**为准（必要时起 dev 用 Playwright 实走取证，勿只读模板文件下结论）；每条发现**回查基线版 md 与近期拍板记录**判定是「本批改口径」「旧有遗留」还是「代码实现缺陷」。
2. **产出审查结果文件** `docs/02-PRD与代码一致性审查/PRD与代码现状一致性审查结果-<批次日期YYYYMMDD>.md`（目录沿用），模板：
   - 头部：审查基准（PRD 终点 commit 号）与来源说明、**标识说明**（旧有遗留条目标题带【<上批日期>已存在】，无标识 = 本批新引入，头部列明新引入 Q 号清单）、分类总表；
   - 正文：**Q 编号条目按类聚合分章**（章序 = 建议处理顺序，每章开头写处理方式）——A 口径矛盾（md 与已拍板决策/代码既定行为冲突，需选边）/ C 代码未跟进 md（默认按 md 落地）/ B 文案措辞微差（整类批量）/ E 代码超出 md（补文档或删功能）/ F PRD 文档自身缺陷（纯 md 修订——git 直改模式下可直接改 md 提交，列明改动供负责人确认）/ G 演示数据与资产；条目格式 `## Qn.【…已存在】模块·差异标题` + 差异描述 + md/代码依据（file:line）+ 原编号；
   - 附录：各路审查组的**审查覆盖说明**（核对范围/实走取证方法/基线对照方法/未覆盖区域）。
3. 本文件**只列差异点，不含处理决策**；本地 commit，交负责人裁决。

## 阶段三：负责人审核

1. 负责人在**两份文件上直接批注决策**（不另建台账）：修订冲突批在 01-改动记录的待确认清单；md↔代码差异批在 02-审查结果对应条目。销项后条目标题加【已解决】。
2. 批注后按标记执行：代码类落地并回归、纯 md 修订类直接改 PRD 正本提交（git 直改）、"采纳现状"类销项——采纳现状意味着 md 要回改，同样直接改正本并在条目注明。
3. 当日 `docs/PRD-review/YYYY-MM-DD.md` 记录闭环与裁决（三段式，见 daily-update-log skill）。git 直改模式下**无「版本切换/删旧文件夹」环节**——基线推进 = 在 01-改动记录尾部记下本批终点 commit。

## 阶段四：改造（负责人拍板后启动，不自动进入）

1. **取舍以工程大原则为评判基准**（根 CLAUDE.md）：①完整表达产品设计想法 ②代码示例让研发易读懂；两者都不沾的投入默认不做。
2. **冻结区先行明确**：挂账条目对应的能力/组件列成禁改清单，写进每个实施 agent 的任务书。
3. **方案先行**：改动面大或涉共享层时，先派架构师做实地盘点与方案设计（**盘点以实数为准，勿直接采信旧审计/旧文档里的数字与归因——已两次实证其失实**），方案存 `docs/调研讨论/`，再分批实施。
4. 按模块分组派并行实施 agent，任务书要素：权威基准（`docs/PRD/数字员工管理端PRD/` 相应模块 md，先通读再动手）、**视觉骨架基准 = 站内既有页面范式 + 设计令牌**（同类页面怎么长就怎么长，不自创样式）、冻结区、共享文件所有权（同一共享组件只归一组改，其余组传参消费；有依赖的组串行；与主工作区并行的高风险组走隔离 worktree）、既有约定（标准件复用、mock 模式 `xxxMock.js`+USE_MOCK 分流、mock 持久化 persist()/改种子 bump version、文案照 md 逐字、密钥 secretMask、测试重写注明对齐日期）、禁止事项（git 写命令/pkill/改 docs 归主流程；dev server 各组用独立端口）。
5. 每组输出：实施摘要（逐条 done/skip+原因）+ 新发现问题（默认按 md 落地并记录，追加进 02-审查结果续 Q 编号）；**每个验证过的闭环批次由主流程复核后独立 commit**（全量测试绿 + build 通过才提，显式路径）。

## 阶段五：验证与提交

1. 全量 `npx vitest run` 必须全绿；`vite build` 通过。
2. 关键改动页面 Playwright 冒烟（页面渲染、探针文案、console/pageerror 零错误）。
3. **视觉验证**：改动页面 Playwright 截图，与**改动前基线截图**及**站内同类页面范式**比对——布局容器（居中/限宽/底色）、卡片分区与区块头、hint 与占位、双主题、输入框编辑态是否白底可输入（只读逻辑泄漏高频回归点）；**测试全绿不构成视觉达标**，主流程收货须亲自看截图。改动大的批次加多角色验收（测试实走 / 产品核 md 口径 / 设计核双主题令牌 / 最终用户视角走查）。
4. 复核冻结区确实未动。
5. 当日 PRD-review 记录改造轮（三段式+影响面）；本地 commit。
6. **阶段推送（GitHub 协同）**：push 不自动、不逐条——仅在负责人指令下把累积的阶段版本一次性推送；推送前过门禁：与远端无分叉（先 fetch 比对）、全量测试绿、build 通过、外发 diff 无密钥、无误收临时文件。推完向负责人报远端点位。
7. **提醒负责人**：两份文件的开放条目待销项；01-改动记录尾部的基线 commit 已推进。

## 硬约束速查

- 发现 PRD md 变更：**先报告 + 询问，不自动启动**；不擅自 commit 负责人未提交的 PRD 改动；push 仅按负责人指令。
- **`docs/PRD/数字员工管理端PRD/` 是长期正本、md 唯一口径**；不再建日期版本文件夹；旧原型与截图仅历史参考。
- 变更范围以 **git diff 基线对比**为准，基线 commit 记在上一份 01-改动记录尾部，本批闭环后推进。
- 每次动工前先 `git pull`；远端有他人提交先合并跑绿；并行/高风险批次走隔离 worktree。
- 冲突点性质判断保守：不确定算冲突。宁全勿漏，微小文案差异也收。
- 修订内部自相矛盾不能自动裁决——必须单独提请负责人二选一。
- 推翻近期拍板的条目（复发项）必须显式提醒（列明是哪次拍板）。
- 改造中对 md↔代码矛盾的默认取向：**按 md 落地 + 记录**；md 与既往拍板冲突的例外——停下提请裁决。
- 决策承载：负责人批注在 01-改动记录 / 02-审查结果 两份文件上，销项标【已解决】；不另建台账。
- 本技能的任何更新须先提请负责人确认，不得直接改（本版即负责人 2026-09-10「git 直改模式」指示的二次改版）。
