# 原型（前端实现）↔ PRD 一致性审计（/prd-audit）—— V1 初稿，待负责人确认

> **本文件是草稿，未生效**：命名、是否接入 CI 门禁、是否需要 README 基线表都还没定，见文末「待拍板的开放问题」。正文先按「假设都通过」的样子写完整，方便你对着挑毛病。

**先讲清楚「原型」是什么**：本项目 2026-09-01 起已降级为纯前端 demo，**项目本身就是「产品交互 demo」**。本技能里说的「原型」= 当前 `frontend/src` 跑起来的这套前端实现，**不是**已退场、只作历史参考的旧交互原型（那套按根 CLAUDE.md 与 [prd-import](../prd-import/SKILL.md)、[test-audit](../test-audit/SKILL.md) 里的铁律，早已不再作为依据）。md 仍是唯一权威口径，本技能只是拿「代码现状」去对「md 口径」，方向和 prd-import 阶段二完全一致，只是触发方式不同。

## 定位与边界（避免跟另外两个技能打架）

- **与 prd-import 的分工**：prd-import 是「PRD 改了之后」的处理流程，阶段二「md↔代码一致性审查」只在 PRD md 出现 git 变更时触发，默认只审变更涉及的模块。**prd-audit 不依赖 PRD 是否最近变了**——用于「PRD 一阵子没动但怀疑代码悄悄漂移」「新模块验收前体检」「定期例行走查」这类场景，可以按任意范围随时重跑。若某次 prd-audit 的范围和最近一轮 prd-import 02-审查结果重叠且中间无新 commit，**直接复用那份结论，不重审**。
- **与 test-audit 的分工**：test-audit 审的是「测试用例」这份说明书写得对不对；prd-audit 审的是「产品实现本身」（页面渲染出来的东西）跟 PRD 说的对不对。审查对象不同，互不替代。
- **只审不改**：prd-audit 只产出报告 + 处置清单，**不在本技能内直接改产品代码或 PRD md**。按 md 落地的实现类差异，改动面小的可以当场小改（见阶段三），改动面大或涉共享层的转 [prd-import](../prd-import/SKILL.md) 阶段四走完整改造流程（冻结区、共享文件所有权等机制不在本技能内重复发明）。
- **不含 C（代码审查）、F（前端自检）两个视角**：那两个视角分别是架构规范和「改造后自检」，不属于「实现↔PRD 一致性」范畴，architecture/可读性问题留给日常 code-review。

## 用法

`/prd-audit [范围]`
- 范围：`all`（全量，按模块分组并行）/ 模块名或路径（如 `岗位`、`src/views/admin/position`）/ `changed`（自上轮终点以来代码有变更的模块——起点读 README 基线表「`/prd-audit` 上轮终点」，**若不引入基线表则去掉这个选项**，见开放问题 2）

## 阶段零：基线

1. `git pull` 拉齐远端；工作区须干净，否则先请用户处理。
2. 起 dev server（复用 `run` 技能的方式，免登录直达 `/admin/...`），供阶段一 B 视角实走取证。
3. 若走 `changed` 范围：读 README 基线表「`/prd-audit` 上轮终点」确定起点。
4. 按范围列出本轮要审的模块清单，向用户报一句「本轮审：xxx」。

## 阶段一：多视角审查（只读，并行派发）

复用 [审查视角清单.md](../prd-import/审查视角清单.md)（不重复造轮子），按模块分组派只读 agent，每组任务书内嵌下列四个视角：

| 视角 | 对应问题 | 主要产出 |
| --- | --- | --- |
| A 产品口径 | 页面文案/提示语/确认弹窗是否与模块 md **逐字**对齐？必填选填/字数上限/状态流转是否对得上《各模块必填选填字段一览表》与 md？ | 口径差异 |
| B 实走验收 | 起 dev 服务**真实走一遍**改动路径，console/pageerror 零错误；交互流逐步取证（操作→期望→实际） | 交互缺陷、mock 语义问题 |
| D 视觉与交互一致性 | 布局骨架、双主题、状态完整性（loading/空态/错误态/边界）与站内同类页面是否一致？`docs/规范/UI/` 设计图仅视觉参考，不按图上数据内容对齐 | 视觉/交互不一致 |
| E 最终用户走查 | 用最普通业务人员视角走一遍：入口找得到吗？文案看得懂吗？错误提示够不够？危险操作有没有确认？ | 可用性问题 |

agent 规则：只读、不改文件；每条发现带 `file:line` 或页面路径 + md 依据（章节）；不确定算问题，宁全勿漏；审查人尽量避开刚写该页面的自己（无法避开时报告里注明）。

## 阶段二：汇总 → 审计报告 + 处置清单

产出 `.review/prd-audit/<YYYYMMDD>/报告.md`（本地，已 .gitignore，不入库；启动时清空上一轮）：

- 头部：责任人、闭环条件、基线起点/终点 commit（若无基线表机制则只写终点）、审查范围、各视角发现数汇总。
- 正文复用 prd-import 02 的分类体系（**不额外发明新类别**）：A 口径矛盾 / B 文案微差 / C 代码未跟进 md（默认按 md 落地）/ E 代码超出 md（先回查近期拍板排除已批准扩展）/ F PRD 自身缺陷（可直接改 md，列明供确认）/ G 演示数据与资产。条目格式同 prd-import：`## Qn.模块·差异标题` + 差异描述 + md/代码依据（file:line）。
- 末尾两份清单：**待裁决清单**（三方矛盾/与近期拍板冲突）→ `docs/03-待决策清单/`；**需他人处理**（按模块分派：01 总览/02 岗位/03 能力/05 治理/06 组织 → 浦月，04 运行 → 曹春林）→ `docs/产品经理待办任务/<人>.md`。
- 报告不 commit（在 `.review/`），向负责人汇报要点，等指示进入阶段三。

## 阶段三：处置建议（分级，不在本技能内直接大改）

- **可当场小改**（无需走完整 prd-import 阶段四）：纯文案措辞对齐 md（B 类）、不涉共享层的单页小遗漏——改完全量测试绿 + build 过，按「一件事一条」commit。
- **转 prd-import 阶段四**：涉及共享层、状态机/规则变更、改动面大于 2 个页面的——本技能只出结论，交给完整改造流程处理。
- **转 03-待决策清单 / 产品经理待办任务**：需要拍板或需要他人处理的，按 prd-import/test-audit 同样规则分派。

## 阶段四：验证与提交（仅当阶段三产生了「可当场小改」时才需要）

1. `npm run test` 全量绿；`npm run build` 通过。
2. 改动页面 Playwright 冒烟（渲染、探针文案、console/pageerror 零错误）。
3. 按「一件事一条」commit，落地结论写进 commit message（报告不入库，commit 是唯一留痕）。
4. 若引入 README 基线表机制：推进「`/prd-audit` 上轮终点」为本轮终点 commit，签名行 `review: prd-audit <范围> ok`。
5. 推送走 PR（同 CLAUDE.md「PR 流程与 CI」），不直推 main。

## 硬约束速查

- md 为唯一口径；「原型」= 当前前端实现本身，不是已退场的旧交互原型，正文/报告里不单独使用「原型」二字（避免和已作废的旧含义混淆），一律写「前端实现」或「demo」。
- 不含 C（代码审查）、F（前端自检）两个视角；只出报告 + 处置建议，不在本技能内跑 prd-import 阶段四那套重型改造机制。
- 报告落 `.review/prd-audit/`，不入库；待裁决进 `03-待决策清单/`，跨人待办进 `产品经理待办任务/`。
- 不确定算问题，宁全勿漏；审查人避开自己刚写的页面。

## 待你拍板的开放问题（这版先按「都通过」写，供你挑）

1. **命名**：拟定 `prd-audit`（跟 `prd-import` 同源、和 `test-audit` 并列）。担心和 `prd-import` 光看名字容易混，要不要换（如 `impl-audit`、`ui-audit`、`demo-audit`）？
2. **要不要 README 基线表 + `changed` 范围**：新增一行能让「自上次审计以来」有明确起点，但也多一处要维护的状态。如果你预期每次都是手动指定 `all` 或某模块，而不是「增量审计」，可以不加这行、去掉 `changed` 选项，技能变得更轻。
3. **要不要接入 `scripts/review-gate.mjs` 强制门禁**：现有门禁是「改了 `frontend/src/` 就要求 test-audit 签名」。如果 prd-audit 也挂同样触发条件，会变成每次改前端代码要求两个审查签名，负担较重。**这版草稿默认不接入**，定位成按需体检（人工发起的健康检查），不做成每次改代码都强制触发的关卡；跑几轮觉得有必要再考虑接入硬门禁。你要现在就接吗？
4. **触发频率**：目前设计成纯手动触发。要不要也考虑挂进 `/loop`（比如每周对 `all` 走一遍出个报告）？
5. **视角够不够**：四个视角（A/B/D/E）是直接复用 prd-import 现成的《审查视角清单.md》，没有新造检查点。如果你觉得「限制规则」这块（必填/选填/字数上限/状态机）需要更细的专属检查点（类似 test-audit 有自己的《视角与操作清单.md》），我可以再拆一份，把《各模块必填选填字段一览表》逐字段的核对方法写成表格。
