# 测试用例多视角审计（/test-audit）—— 2026-09-17 负责人批准修订：基线表 / 待决策入 03 / 待办文件夹 / PR 流程

**定位**：本项目是纯前端 demo，测试的价值只有两条（对应根 CLAUDE.md 工程大原则）——①守住「页面表达的产品设计想法」不被后续改动悄悄改掉；②用例本身是给研发看的**行为说明书**。审计的裁决标准也只有这两条：一条用例既不守行为、也说明不了行为，就是无效用例。

**已知教训（2026-09-11 三次同源漏判）**：测试全绿 ≠ 页面正常——桩组件会吞掉真实挂载期错误（TDZ 白屏 15 页）、按命名约定扫描总漏掉不守约定的文件。所以本技能每个视角都要求「按约定扫 + 按实际结果兜底核查」两手。

**用法**：`/test-audit [范围] [--dry-run]`
- 范围：`all`（默认，全量，文件数以阶段零实数为准，按模块分组并行）/ 模块名或路径（如 `岗位`、`src/components/position`）/ `changed`（自上轮终点 commit 以来代码变更所涉及的模块；**起点只读仓库根 `README.md`「基线表」的「`/test-audit` 上轮终点」**，不看任何报告尾部）
- `--dry-run`：只做阶段一、二，产出报告与处置清单，不改任何文件

## 阶段零：基线（必须先做）

1. `git pull` 拉齐远端（开工先拉）；工作区须干净，否则先请用户处理。
2. `cd frontend && npx vitest run` 记录基线：文件数 / 用例数 / 全绿；**同时查 origin/main 最近一次 CI 结论**（`gh run list --branch main --limit 1`）——CI 跑 Node 22，本地绿 CI 红时以 CI 为准，先查 Node 差异（见 `.github/workflows/ci.yml` 注释）。**基线不绿则停止**——先修红再审，不在红的基础上做增删。
   上一轮的 `.review/test-audit/` 此时清空（终点已在基线表，报告不再承载）。
3. 盘点测试资产（以实数为准，勿采信旧文档数字）：`find src -name '*.test.js'` 按目录计数；`*.browser.test.js` 单列（归 `vitest.browser.config.js`，node 环境跑它们是假绿）；`it.skip/.only/.todo` 计数（现状为 0，审计结束也必须为 0）。
4. 列出「无任何测试引用」的 views / components / stores / `*Mock.js`，作为覆盖视角的输入。

## 阶段一：多视角审查（只读，并行派发）

按范围分组（参考分组：岗位系 / 知识库 / 连接器三件套 / 专家·技能·模型 / 治理域 / 组织域 / 共享层 utils+components+stores / 卫生守卫与 browser 用例），**每组一个只读 agent，任务书内嵌全部六个视角**（视角清单与逐项检查点见 [视角与操作清单.md](视角与操作清单.md)）：

| 视角 | 问的问题 | 主要产出 |
| --- | --- | --- |
| A 产品口径 | 用例断言的文案/规则/状态流转是否与 `docs/PRD/数字员工管理端PRD/` md 一致？md 里的规则哪些没有用例？ | 冲突用例、缺口用例 |
| B 代码现状 | 用例引用的组件/函数/字段/路由还在吗？mock 的模块被测对象还 import 吗？断言的是已删功能吗？ | 失效用例、幽灵 mock |
| C 可信度 | 用例会不会永远绿：只断言 mock 被调用、断言常量、桩组件吞掉挂载错误、顺序依赖、环境声明缺失 | 假绿用例、需提升断言 |
| D 可读性 | 头注日期/依据是否过期（尤其「照原型」措辞，原型已退场）、describe/it 是否说清「什么情况→期望什么」、一文件是否塞了多个主题 | 头注修正、改名、拆分 |
| E 变更增量 | 自基线表终点以来的 commit 改了哪些代码但没动测试？commit message 与 02 审查结果里记的「踩坑」有没有防回归用例？ | 缺口用例、防回归用例 |
| F 结构覆盖 | 阶段零列出的无测试文件里，哪些承载了产品规则（状态机、校验、mock 持久化 persist/version）？哪些是纯壳（占位页）不值得测？ | 缺口用例（分优先级）、明确不测清单 |

agent 规则：
- **只读**，以文本返回报告，不写文件（子 agent 写 scratchpad 会被拦）。
- 每条发现必须带 `file:line` + 判定依据（md 路径与条款 / 代码位置 / 复现方式）；判 A 视角冲突时**回查基线表起点以来的 PRD commit 与 02 审查结果里的拍板注**，区分「md 改口径」「代码未跟 md」「用例自己错」。
- 三方（md / 代码 / 用例）不一致时的归因规则：md 为唯一口径；用例≠md 且代码=md → 用例错，更新；用例=代码≠md → **代码缺陷，不在本技能内修**，用例暂不改、列入报告「代码缺陷」清单交负责人（修好代码后再补用例，不用 `it.skip` 占坑）；三方各不同 → 提请裁决。
- 不确定算「待裁决」，宁全勿漏。

## 阶段二：汇总 → 审计报告 + 处置清单

主流程合并各组报告，去重、按处置类型聚合，写 **`.review/test-audit/<YYYYMMDD>/报告.md`**（本地，已 .gitignore，**不入库**；2026-09-17 负责人定——审查产物只在本地，入库的是改出来的用例 commit、待办、03 待决策和签名行；技能启动时先清空上一轮）：

- 头部写清：责任人、闭环条件（T 处置清单执行完、J 项全部裁决）、基线表起点 commit。
- 头部：基线数字（文件/用例/绿）、审计范围、**起点与终点 commit**（终点同时写入 README 基线表，见阶段四）、各视角发现数汇总表。
- 正文按处置类型分章，章序 = 执行顺序：**删除失效 → 更新冲突 → 修正头注/改名 → 合并/拆分 → 提升断言 → 补齐缺口 → 建议不测**。条目格式 `## Tn.视角·文件·一句话`：现状（引用例原文）→ 依据（md/代码定位）→ 处置动作 → 风险等级。
- 末尾两份清单：**代码缺陷清单**（K 项：用例暴露的实现问题——**按模块分派进 `docs/产品经理待办任务/<人>.md`「待处理」表**：01 总览 / 02 岗位 / 03 能力 / 05 治理 / 06 组织 → `yuepu`，04 运行 → `clcao`；报告里只留索引）、**明确不测清单**（纯壳页、占位页，写明理由免得下次再审）。
- **待裁决清单（J 项）单独成文** `docs/03-待决策清单/测试审计待决策-YYYYMMDD.md`（三方矛盾 / 与近期拍板冲突 / 整文件删除；每条写「背景 → 选 A 还是 B → 团队建议」，文件头四行，闭环条件 = 每条批复且落地），报告末尾只放指向。
- `--dry-run` 到此为止；报告不 commit（在 .review/），向用户汇报要点。

## 阶段三：处置（默认自动执行，风险项停下确认）

**自动执行（无需确认）**：删除断言已删功能/引用已不存在符号的单条用例；按 md 更新冲突用例的文案与期望；修正过期头注与命名；合并重复；提升假绿断言；补齐缺口用例；修正环境声明。
**必须先确认（列明确认点：哪个文件、为什么、影响面）**：删除整个测试文件；删除或改写与近期负责人拍板相关的用例；改动卫生守卫（`staticHygiene` / `moduleGraph`）规则；任何要改产品代码才能让用例成立的情形（一律不改，进代码缺陷清单）。

写用例的约定（补齐/更新时遵守，细则见清单文件）：
- 头注写明「YYYY-MM-DD 对齐 <md 路径 §节>」与覆盖范围；用 DOM 的文件顶部 `// @vitest-environment jsdom`。
- 用例名用大白话说「什么情况→期望什么」，断言落在**用户可见结果**（渲染文案、状态、路由、持久化数据），不只断言 mock 被调用。
- 每条独立可跑（vitest 默认 shuffle）：不依赖前一条留下的状态；用到 localStorage 的在 `beforeEach` 清理。
- 桩掉重组件时，至少保留一条**真实挂载**冒烟（挂载不抛错、关键探针文案在），防 TDZ 类初始化错误假绿。
- mock 层写点须验证 `persist()` 落盘与刷新后读回；改种子的验证 version bump。
- 不为凑数写用例：一条用例守一条规则，守不住任何规则的不写。

## 阶段四：验证与提交

1. `npx vitest run` 全绿；补/改用例再用两个不同 `--sequence.seed` 复跑一次（排除顺序依赖）；`npm run build` 通过。
2. **删掉的用例逐条反证**：对每条删除，确认「该用例守的行为已不存在」或「已有另一条用例守同一行为」，二者取一写进报告；没有反证的不删。
3. **新增用例做「能红」验证**：至少抽样把被测行为临时改坏一次确认用例会红（改完还原），或在报告中说明用例断言的是哪条真实规则。
4. 报告尾部补「处置结果」：每条 Tn 标 done / skip+原因 / 待裁决；更新前后数字对比（文件、用例、无测试文件数）。**每条落地的处置在对应 commit 说明里写清**（报告不入库，commit 是唯一留痕）。
5. 按「一件事一条」commit（显式路径）：删除失效一条、更新冲突一条、补齐缺口按模块各一条；提交前每条都要全绿。commit message 写清用例增删数与涉及页面（不写日记录，PRD-review 已停用）。
6. **推进基线表 + 签名**：处置全部 done 后，把仓库根 `README.md`「基线表」的「`/test-audit` 上轮终点」改为本轮最后一条测试改动 commit，该 commit 说明末尾加签名行 **`review: test-audit <范围> ok`**（如 `review: test-audit changed 36ff5a3..abc1234 ok`；CI 软门禁 `scripts/review-gate.mjs` 凭此判断）。
7. **推送走 PR**（CLAUDE.md「PR 流程与 CI」）：开分支与 push **按负责人指令**——`git switch -c test/<简述>` → `git push -u origin` → 开 PR、Enable auto-merge；推前 fetch 无分叉、全量绿、build 过。不直推 main。

## 硬约束速查

- 基线不绿不审；审完 `skip/only/todo` 仍为 0；browser 用例不用 node 配置跑。
- **不改产品代码**去迁就用例；用例暴露的实现问题只记录、交负责人。
- 删除必须有反证，整文件删除必须先确认；与近期拍板相关的用例先确认再动。
- md 为唯一口径，原型措辞只作历史出处保留，不再作为断言依据。
- 报告只写实数与可定位的发现，不写「建议加强覆盖」这类空话；每条 Tn 可独立执行、独立回退。
- push 仅按负责人指令且只走 PR；起点/终点只认 README 基线表；报告在本地 `.review/` 不入库；K 项进待办文件、J 项进 03；收口 commit 带签名行。
- 本技能更新须先提请负责人确认（本版 = 负责人 2026-09-17 批准的修订稿 7.3 + 当日新增机制）。
