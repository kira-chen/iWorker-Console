# 测试审计：六个视角的检查点 + 处置操作目录

供 /test-audit 阶段一派发给各组 agent 的任务书内嵌使用。每个检查点都写了「怎么查」——**先按约定扫，再按实际结果兜底**，只按命名/常量扫一遍必漏。

## 视角 A · 产品口径（用例 ↔ PRD md）

依据：`docs/PRD/数字员工管理端PRD/<模块>/prd.*.md` + 《各模块必填选填字段一览表.md》。原型已退场，用例里「照原型」的断言一律重新对 md。

| 检查点 | 怎么查 |
| --- | --- |
| 断言的文案是否与 md 逐字一致 | 抽取用例里的中文字符串字面量（toast、按钮、占位、确认框、空态），在对应 md 里搜；搜不到的逐条判：md 改了 / 用例编的 / 代码超出 md |
| 断言的规则是否与 md 一致 | 必填/选填、字数上限、状态流转（发布→审核中→撤回…）、软上限条数、默认值——对 md 条款与一览表 |
| md 规则是否有用例 | 把 md 里每条「必须/不允许/默认/上限/提示」句子当作规则清单，逐条找守它的用例；没有的记缺口，按「守的是不是用户可见规则」定优先级 |
| 用例是否守着已被 md 推翻的旧口径 | 对照基线表起点以来 `git log -- docs/PRD/` 的 feat / docs(prd) 提交与其 commit 说明里的「按 Qn」注（02 审查结果在本地 .review/，不入库），凡口径变更过的点看用例有没有跟着改 |

归因规则（三方不一致）：用例≠md 且代码=md → 用例错（更新）；用例=代码≠md → 代码缺陷（记录，不改代码不改用例）；三方各异 → 待裁决。

## 视角 B · 代码现状（用例 ↔ 被测对象）

| 检查点 | 怎么查 |
| --- | --- |
| 引用的组件/函数/字段/路由还在吗 | 用例 import 的路径能否解析；`vi.mock('@/api/xxx')` 里定义的方法名是否仍在真实模块导出；用例访问的 `wrapper.vm.xxx`、`store.xxx`、mock 数据字段名是否仍存在 |
| 幽灵 mock | 被测组件已不再 import 某模块，但用例还在 `vi.mock` 它——无害但误导读者，删 |
| 断言已删功能 | 用例名/断言里的功能词（如某按钮、某页签、某状态）在当前源码里是否还存在；断言通过只是因为「没有 = 没有」的空断言 |
| 桩组件与真实组件 props/事件是否还对得上 | 桩定义的 props / emits 名与真实组件比对；真实组件改了事件名而桩没改，用例会假绿 |
| 分支开关是否还有两条腿 | 如 `prototype` 这类 opt-in prop：用例是否只测了一侧；另一侧还有人用吗（没人用 → 提请是否连开关一起退役，用例不单独删） |
| 测试目标是否已被整体替换 | 组件被重写/改名后旧用例文件还留着（文件名与现组件名对不上是线索） |

## 视角 C · 可信度（用例会不会永远绿）

| 检查点 | 怎么查 |
| --- | --- |
| 只断言 mock 被调用 | `expect(api.xxx).toHaveBeenCalled` 之后没有任何用户可见结果断言 → 提升：断言渲染文案 / 状态 / 路由 / 持久化数据 |
| 断言常量或同义反复 | `expect(x).toBe(x)`、断言自己在用例里塞进去的值原样出来 |
| 桩组件吞掉挂载错误 | 页面级用例把 `el-table`/`el-drawer`/分页条等全桩掉——2026-09-11 分页条 TDZ 白屏 15 页而单测全绿即此。要求每个页面级用例文件至少一条**真实挂载**冒烟（挂载不抛、关键探针文案在） |
| 顺序依赖 | 用两个不同 `--sequence.seed` 跑；模块级可变状态（`let` 计数器、共享 mock 数据对象）未在 `beforeEach` 重置的标出 |
| 环境声明 | 用了 `document`/`localStorage`/挂载但文件头没有 `// @vitest-environment jsdom`（node 下能过多半是没真挂载） |
| browser 用例混入 node 配置 | `*.browser.test.js` 之外的文件做视觉/布局断言（`getBoundingClientRect`、计算样式）在 jsdom 下全是 0，假绿 |
| 定时器/异步未等待 | `setTimeout` 逻辑没 `vi.useFakeTimers`、异步没 `await flushPromises/nextTick` 就断言 |
| 过度指定 | 断言整段 HTML / 快照，改一个 class 就红，训练人无脑更新快照 |

## 视角 D · 可读性（用例是给研发看的说明书）

| 检查点 | 怎么查 |
| --- | --- |
| 头注是否过期 | 头注日期与「对齐依据」：写「照原型 / 原型 v2 / 原型复刻」的改为「对齐 md §节」，原型措辞作历史出处保留在括号里；头注列的覆盖项与实际用例对不上的改 |
| 用例名是否说清「什么情况→期望什么」 | 反例：`it('works')`、`it('测试发布')`；正例：`it('无工具的服务点发布 → 前端拦截并提示"至少添加一个工具"')` |
| 一文件多主题 | 一个文件里 describe 跨了不相干功能（或 >60 条用例），拆；反之同一组件的用例散在 4 个文件里且各自 1 条（如 `adminSkillEdit*.test.js` 系列），评估是否合并——合并以「读者找一个功能的用例只用开一个文件」为准 |
| 桩/mock 样板重复 | 多文件重复几十行相同 EP 桩定义 → 抽到 `__tests__/helpers/`（只抽确实完全相同的，别为抽而抽） |
| 魔法数字/魔法字符串 | 用例里 `168`、`'1003'` 无注释——写明来源（COL.TIME / 后端错误码含义） |

## 视角 E · 变更增量（最近改了代码，测试跟了吗）

| 检查点 | 怎么查 |
| --- | --- |
| 改了代码没改测试 | `git log --since=<上次审计> --name-only` 取改动的 .vue/.js，看同 commit 或之后有无对应 `__tests__` 变动；没有的逐个判断改动是否含行为变更 |
| 近期「踩坑」有没有防回归 | 读基线表起点以来的 commit message（`git log --grep=修\|fix\|坑`）与 02 审查结果里「已修」条目，每个坑找对应用例；没有的补（如：分页条 watch 在 const 之前的 TDZ → 真实挂载冒烟；跳页框提交后清空 → 断言回填当前页） |
| 他人提交的改动 | 他人 commit 涉及的模块，用例是否随之更新（他们可能只改了代码） |
| 新增 mock 写点 | 新增的 `xxxMock.js` 写方法有没有 persist() 与刷新读回的用例 |

## 视角 F · 结构覆盖（谁没有测试，值不值得测）

| 检查点 | 怎么查 |
| --- | --- |
| 无测试文件清单 | 阶段零输出；对每个文件分三档：**承载产品规则**（状态机/校验/mock 持久化/权限显隐）→ 补；**纯展示壳**（占位页、静态说明页）→ 明确不测并写理由；**共享层**（utils/公共组件/stores）→ 有跨页影响的补 |
| mock 层约定 | 每个 `*Mock.js`：有 persist() 的是否测了落盘+读回；有 version 的是否测了旧版本数据被重置 |
| 卫生守卫扩充 | staticHygiene 只收「实测可靠、存量 0 命中」的规则；审计中发现的全站性约定（如硬编码列宽、缺 nowrap）若能零误报静态查出，建议新规则，**加规则须先确认** |

## 处置操作目录

| 操作 | 何时用 | 是否需确认 | 反证/验证要求 |
| --- | --- | --- | --- |
| 删除单条用例 | 守的行为已不存在；或与另一条重复 | 否 | 报告里写明「行为已删于 commit X」或「与 Tn 重复」 |
| 删除整个文件 | 被测对象已整体移除/重写 | **是** | 列明文件、被测对象去向、有无替代用例 |
| 更新冲突用例 | 用例≠md 且代码=md | 否（涉近期拍板则**是**） | 头注加对齐日期与 md §节 |
| 修正头注/改名 | 过期依据、说不清的用例名 | 否 | 不改断言 |
| 合并 | 同一功能散在多文件、样板重复 | 否 | 合并后用例数不减（或减的都是重复，逐条列） |
| 拆分 | 一文件多主题 / 超长 | 否 | 拆后文件名与被测对象对应 |
| 提升断言 | 假绿：只断言 mock 调用、常量、桩吞错误 | 否 | 做一次「能红」验证 |
| 补真实挂载冒烟 | 页面级用例全桩化 | 否 | 挂载不抛 + 探针文案在 |
| 补缺口用例 | md 规则/踩坑/新增写点无用例 | 否 | 一条用例守一条规则；做「能红」验证 |
| 修环境声明 | 用 DOM 无 jsdom 声明 / browser 用例放错配置 | 否 | 在正确环境下重跑 |
| 抽公共桩 helper | ≥3 文件完全相同的桩样板 | 否 | 抽后各文件行为不变、全绿 |
| 建议新卫生规则 | 全站约定可静态零误报查出 | **是** | 存量 0 命中实证 |
| 标记「明确不测」 | 纯壳页 | 否 | 写理由进报告，避免反复审 |
| 记录代码缺陷 | 用例=代码≠md | — | 不改代码、不改用例、不 skip；交负责人 |
| 待裁决 | 三方各异 / 与拍板冲突 | — | 列新旧口径与拍板出处 |

## 报告条目模板

```markdown
## T7.C·src/views/admin/__tests__/adminMcp.test.js:88·「发布成功」只断言 API 被调用
**现状**：`expect(marketApi.publishMcpService).toHaveBeenCalledWith(...)` 后无渲染断言；状态列改坏也不会红。
**依据**：`03能力/连接器/MCP/prd-连接器-MCP.md` 操作列条款「审核中【编辑】仍展示但不可点击」「根据状态展示【撤回】」。
**处置**：提升断言——发布后断言状态标签文案「审核中」、【编辑】禁用、操作区出现【撤回】。风险：低。
```
