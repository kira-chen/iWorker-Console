# pixel-audit · 像素级对齐差异工具

把「原型长什么样」和「我们的页面长什么样」逐个容器、逐个属性摆到一张表上对比，
自动列出哪里不一样。

## 为什么要有这个工具

2026-09-10 岗位详情对齐那两轮，我们最初的做法是「负责人指着截图说哪里不对 → 改一处」。
结果被批评是「半成品」——因为**有些差异肉眼根本看不出来，连比对 DOM 结构都看不出来**。
换成脚本全量对表之后，一次性抓出了两个真硬伤：

- 代码里引用了 `--bg-subtle` / `--fill-subtle` 两个**在 tokens.css 里压根不存在**的令牌，
  底纹实际是透明的，但页面看上去「好像也还行」，没人发现；
- 工作档案两栏比原型**整体窄了 102px**，因为三层容器各自内缩了一次，叠加出来的。

所以这个工具的价值不是「省事」，是**能查出人查不出来的东西**。

## 怎么用

需要两个终端。

**终端 1** —— 把我们自己的页面跑起来：

```bash
cd frontend
npm run dev
```

**终端 2** —— 跑对表：

```bash
cd frontend

npm run audit:pixel                    # 跑全部单元
npm run audit:pixel -- --unit=agents   # 只跑 Agent 与技能这一屏
npm run audit:pixel -- --headed        # 带浏览器界面跑（调选择器时看得见）
```

如果 dev 服务不在默认的 5173 端口（比如被占了自动跳到 5174），加个环境变量：

```bash
PIXEL_AUDIT_BASE=http://localhost:5174 npm run audit:pixel
```

跑完输出两个文件（在 `tools/pixel-audit/out/`）：

| 文件 | 给谁看 | 内容 |
| --- | --- | --- |
| `report.md` | 人 | 主差异表 + 豁免命中 + 豁免自证统计 |
| `report.json` | 机器 | 同样的内容，结构化。可以跟上一轮的 json 比，看差异是变多还是变少 |

## 报告怎么读

报告分五节，**按重要性从上往下**：

1. **主差异表** —— 这就是要处理的。每行是「哪个容器 · 哪个属性 · 原型是多少 · 我们是多少」。
   刚对齐过的页面，这一节应该基本是空的。
2. **容器未命中** —— 选择器没抓到东西。**先怀疑是选择器写错了**（尤其是下面「坑 1」那个），
   再怀疑是页面结构真的少了这块。
3. **跑挂的单元** —— 进入路径走不通，多半是选择器过期了。
4. **豁免命中** —— 确实有差异，但负责人已经拍板不改。不用管，但可以看一眼数量对不对。
5. **豁免自证统计** —— 见下面「豁免清单的规矩」。

## 三个探针坑（这是本工具最值钱的部分）

写这类对表脚本，有三个地方特别容易踩，踩了之后**报告会看起来很像回事，但整张表是错的**。
工具已经把三个坑都堵在代码里了，这里说明是什么坑、堵在哪，免得后来人改代码时又把它捅开。

### 坑 1：隐藏面板陷阱 —— 会让整张差异表作废

Element Plus 的 `el-tabs` 会把**所有页签的内容同时渲染进 DOM**，只是除当前页签外都藏起来。
岗位详情有 8 个页签，也就是说 DOM 里同时存在 8 份 `.pd-card`。

这时候 `document.querySelector('.pd-card')` 抓到的，很可能是**某个隐藏页签里的那张卡**。
隐藏元素的宽高是 0，padding 读出来也是 0。于是报告会显示：所有属性「原型有值、现状 0」——
看起来像页面整个塌了，实际上页面好好的，是探针抓错了元素。

> 09-10 那轮真实踩过：知识页签的搜索框首轮实测 176px，一看就不对；
> 修掉探针之后实测跟原型逐值一致。那个 176px 就是隐藏 pane 的假读数。

**堵在哪**：`collect.js` 的 `hasRealSize()` / `pickVisible()`。
所有查询都不用 `querySelector` 取第一个，而是把候选全取出来，**筛掉宽高为 0、
display:none、visibility:hidden、祖先带 aria-hidden 的**，取第一个真正有尺寸的。
另外 `run.js` 的 `waitFor` 等的是 `visible` 而不是 `attached` —— 等 attached 会立刻通过，
因为隐藏 pane 本来就 attach 着。

### 坑 2：底色归属陷阱 —— 会报出假的「底色丢失」

表格行的底色，**原型写在 `<tr>` 上，Element Plus 写在 `<td>` 上**。
而且 EP 的 `td` 自带一层背景色，**会盖住 `tr` 上的底色** —— 就算你在 tr 上设了色也看不见。

所以：

- 只比 tr：得出「原型 tr 有色、我们 tr 透明」→ 假的「底色丢了」
- 只比 td：得出「原型 td 透明、我们 td 有色」→ 假的「多了个底色」

两边都是错的。

> 前面提到的「Agent 行底纹一直是哑的」那个真硬伤，就是**同时采了 tr 和 td**
> 之后才辨出来的 —— 两边都是 transparent，那才是真的丢了。

**堵在哪**：`collect.js` 的 `isTableRowish()`。
容器选择器命中 `tr` / `td` / `th` 时，工具会**自动把 tr 和它的第一个 td 都采下来**，
在报告里分成两行，名字带 `[tr]` / `[td]` 后缀，并在「采集说明」一节里写清楚为什么。

配置里想触发双采，容器选择器写到行一级就行，比如
`{ proto: '.pd2-table tbody tr', app: '.pd-table .el-table__body tbody tr' }`。

### 坑 3：原型导航陷阱 —— 会让你对着一份早就失效的源码干活

原型是**一个 html 文件里多层覆写**：同一个渲染函数被重新定义十几次，后面的覆盖前面的。
两个后果：

**(a) 不能读被覆盖的旧层源码。**
比如原型 L1856 的 `agentsPane` 渲染的是泳道看板，但它被后面的层覆盖了，
最终生效的是跟我们同构的二级表格。09-10 的排查报告原话：「若对照源码旧层会严重误判」。

**(b) 进入路径要用结构选择器，而且必须以最终生效态为准。**
这个工具**第一版就栽在这里**：照着源码 L1872 写了 `[data-pd-action="tab"]`，
结果 6 个单元全部超时跑挂 —— 因为那一层被覆盖了，最终生效态里
`data-pd-action` **一个都不存在**，实际属性是 `data-pfix="tab"`。
真相是把原型真跑起来、把 `.pd2-tabs` 的 innerHTML 打出来才看到的。

另外别用文字匹配找菜单：原型侧栏「岗位」和「岗位管理」两项，
文字匹配会同时命中，而「岗位管理」根本没接模块，点了只弹一句 toast。
要用 `button[data-module="positions"]` 这种结构入口。

**堵在哪**：`units.config.js` 顶部的大段注释 + `protoTab()` 上方的说明。
规矩是：**原型侧的选择器一律来自「浏览器里跑出来的最终 DOM」，不许从 html 源码眼读。**
调新页面时用 `--headed` 跑，或者临时写几行把目标区域的 innerHTML 打出来看。

## 报告里为什么有「已滤除的属性无关差异」

除了「豁免」（真差异但负责人拍板不改），工具还会**直接扔掉一类差异**：
两边数值确实不一样，但**在屏幕上根本看不出来**。这类不进任何一张表，只在报告头部报个总数。

首轮实跑时人格页签报了 45 条主差异，其中 19 条是这种噪声。四类：

| 类型 | 例子 | 为什么不算差异 |
| --- | --- | --- |
| 0 宽边框的颜色 | `border-top-color: rgb(31,41,36)` vs `rgb(55,53,47)` | 边框宽度是 0，这个颜色一个像素都画不出来（CSS 没设边框色就取 currentColor，于是文字色被当成边框色报出来） |
| 非 flex/grid 容器的 gap | `gap: normal` vs `24px` | 容器不是 flex 也不是 grid，gap 不生效 |
| 无文字容器的行高/字色 | `line-height: normal` vs `22.5px` | 这个元素自己没有文字节点（纯布局 div），行高和字色不产生视觉差 |
| 殊途同归的内外距 | 原型把留白记在外层 padding，我们记在内层 padding | 两边 x/y/宽高**四项全一致**时，留白记在谁头上不影响观感 |

最后一类是实跑才发现的：岗位详情面板根，原型的留白在 `.pd2-content` 上、
我们的在 `.pd-pane` 上，两边实测都是 `x=312 / width=1180` 完全对齐，
但逐属性比会报出 4 条假差异 × 5 个页签 = 20 条噪声。

另外**颜色允许每通道差 2**：站内令牌是从原型取色后按设计规范落的整数，
常见 `rgb(221,228,224)` vs 原型 `rgb(223,229,225)` 这种，屏幕上分辨不出来。
色相真的不同、或者一边透明一边不透明，仍然照报。

> **想看被滤掉的是什么**：把 `report.js` 里 `isIrrelevant()` 的 `return true` 临时改成
> `return false` 再跑一次就全出来了。别长期这么留着，会淹没真问题。

## 加一个新页面的审计

**只改 `units.config.js`，不用动工具代码。** 往 `units` 数组里加一个对象：

```js
{
  key: 'skills',                        // --unit=skills 用这个
  name: '技能列表页',                    // 报告里显示的名字
  proto: {
    steps: [                            // 原型侧：怎么点到这一屏
      { click: 'button[data-module="skills"]' },
      { waitFor: '.skill-table' }
    ],
    root: '.view-root'                  // 根容器：所有坐标相对它算
  },
  app: {
    url: '/admin/skills',               // 现状侧 URL（相对 dev 服务）
    steps: [{ waitFor: '.admin-table' }],
    root: '.admin-main'
  },
  containers: {                         // 容器映射表：语义名 -> 两侧选择器
    白卡:   { proto: '.proto-card',  app: '.admin-card' },
    卡头:   { proto: '.proto-head',  app: '.admin-card-head' },
    表格首行: { proto: '.tbl tbody tr', app: '.el-table__body tbody tr' }
  }
}
```

`steps` 支持四种动作：

| 写法 | 作用 |
| --- | --- |
| `{ click: '选择器' }` | 点击，会自动等元素可见 |
| `{ waitFor: '选择器' }` | 等元素出现且真的有尺寸 |
| `{ waitTimeout: 300 }` | 硬等 300 毫秒。**慎用**，优先用 waitFor |
| `{ eval: 'JS 表达式' }` | 在页面里执行一段 JS（原型的状态机偶尔要用） |

**`root` 为什么重要**：所有 x/y 坐标都是相对 root 算的。
这样即使原型和我们的页面整页偏移不一样（侧栏宽度不同之类），也能公平地比内部布局。

**几何属性有 1px 容差**（x/y/width/height），因为两边渲染路径不同，1px 抖动是噪声。
padding / border / 圆角这些盒模型属性**不给容差**，差 1px 就报。
容差可以调：`--tolerance=2`。

## 豁免清单的规矩

`exemptions.js` 里登记的是「**确实有差异，但负责人已经拍板不改**」的那些。
命中豁免的差异不进主差异表，单独归到报告第四节。

目前内置三条，都是 2026-09-10 负责人拍板的：

| 编号 | 是什么 | 为什么不改 |
| --- | --- | --- |
| T1 | 全站表格密度（表头/行高/单元格内距/字号） | 由 theme.css + admin-shell.css 统一定义、26 个组件共用，改一处全站波及 |
| T2 | 共享 DrawerEditor 抽屉的 body padding | 出自全站共享组件，改则所有抽屉一起变 |
| T3 | 原型用了站内没有的值（9px 圆角、18px 间距、按钮绿值） | 按「找不到令牌不自造」维持站内规范 |

### 新增豁免的硬要求

1. **必须先经负责人裁决。** 开发不能自己判断「这个差异无所谓」就加一条。
2. **必须写全五个字段**，一个都不能少：
   - `id` —— 编号
   - `title` —— 一句话说清是什么差异
   - `decidedOn` —— 裁决日期
   - `decidedBy` —— 裁决人
   - `source` —— **出处，优先写裁决所在的 commit 号**（台账文件会归档，commit 永远查得到），让人能翻回去看当时怎么议的
3. **判定条件要用代码写死**（`match()` 函数），不能只写一段文字描述。
   文字描述会被后来人理解宽或理解窄，代码不会。
4. `condition` 字段用大白话写清楚 `match()` 到底在判什么，方便不读代码的人复核。

### 豁免会自己证明自己还有用

豁免最怕的是**烂成僵尸配置**：某条豁免对应的差异其实早就没了（代码重写过了），
但它还挂在文件里，给人一种「这块还有历史包袱」的错觉，下次没人敢动。

所以跑批会统计每条豁免**这一轮命中了多少次**，写在报告第五节。
**命中数是 0 的会被显式标成「⚠️ 可能已失效/多余，请复核」。**

看到 0 命中，两种可能，都需要人来判断：

- 差异本身已经消失了 → **这条豁免该删掉**；
- 这一轮跑的单元没覆盖到它管的地方（比如 T2 管抽屉，但这轮没跑任何带抽屉的单元）
  → **该把配置扩上去**，让豁免有机会被验证。

## 工具不做什么

- **不改任何业务源码。** 它只读页面、出报告。改不改、怎么改，是人的决定。
- **不判断差异该不该修。** 主差异不为 0 也不会让退出码变成失败（只有「跑挂了」才算失败），
  因为「要不要修」是负责人的判断，不是工具的判断。
- **不解析原型 html 源码。** 只认浏览器跑出来的最终 DOM，理由见坑 3。

## 文件结构

```text
tools/pixel-audit/
├── run.js             CLI 入口：解析参数、开浏览器、走进入路径、串起全流程
├── collect.js         盒模型采集器（坑 1、坑 2 堵在这里）
├── report.js          比对 + 生成 Markdown/JSON 报告
├── units.config.js    审计单元配置（坑 3 的说明在这里；加新页面只改这个文件）
├── exemptions.js      豁免清单（含自证机制）
├── README.md          本文件
└── out/               跑批输出（report.md / report.json）
```
