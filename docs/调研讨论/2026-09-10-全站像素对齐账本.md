# 全站像素对齐差异账本（2026-09-10）

> 用 `frontend/tools/pixel-audit` 全量扫描原型与现状，产出**只扫不修**的全局账本，供负责人定修复方案。
> 跑法：`cd frontend && npm run audit:pixel`（可 `--unit=xxx` 单跑）。**账本可复现**：连跑两次除时间戳外逐字节一致（实测 STABLE）。

## 一、大白话总结论

全站 31 个审计单元跑下来，**1602 条主差异**。但这不是「1602 个各自独立的毛病」——按属性归类后一眼可见：**几乎每类差异都覆盖 20~31 个单元**（共 31 个），说明它们出自少数几处共享层（全站按钮、表格、输入控件、分页、页头、令牌色值），**改一处即全站受益**。逐页去修是错的，也修不完。

同时印证了「先扫全站再动手」这个决定：如果按页修，光描边色一类就要在 31 个页面各改一遍，且必然改漏。

## 三、系统性根因分组（两路扫描汇总，改一处全站受益）

**G1 按钮体系（约 130 条，12/12 能力域单元 + 8/13 治理域单元全覆盖）**
现状是 Element Plus 原生按钮，原型是自绘按钮：`padding-top/bottom 0→8px`、`line-height 19.5px→14px`、主按钮四边 `border-width 0→1px` 且色值不同、次按钮描边色不同、`font-weight` 主 600→500 / 次 400→500。

**G2 输入类控件的描边画法整体不同（9/13 单元，单类最广）**
原型用真 `border: 1px solid rgb(214,221,217)` + `radius 8px`；现状 Element Plus 用 `box-shadow: 0 0 0 1px inset rgba(55,53,47,0.1)` + `radius 6px`，`border-width` 全为 0。**这是「描边根本不是同一种画法」，不是色值差一档**。命中：搜索框、筛选下拉、文本输入、权限域等。

**G3 表格描边与行底色（7~8 单元，含全覆盖的 border-bottom-color）**
出自 theme.css / admin-shell.css：表头与数据行 `border-bottom-color` 站内半透明 `rgba(55,53,47,0.06)` vs 原型不透明 `rgb(223,229,225)`；行底色 `transparent → rgb(255,255,255)`（底色搬了家，靠 tr/td 双采才辨得清）。

**G4 分页控件整体差一档（5~10 单元，全站同一份实现）**
`font-weight 400→600`、`width 30→28px`、`font-size 12→13px`、`gap 6→5px`、底色与主色值不同。

**G5 页头与次要文字色令牌整体偏移（6~8 单元）**
标题 `line-height 34→32.5px`、`color rgb(34,34,34)→rgb(55,53,47)`；副文案 `color rgb(104,115,109)→rgb(120,119,116)`，同时波及分页信息、对象描述、技能描述——**是一个次要文字色令牌的整体偏移**。

**G6 品牌绿两套值（6 单元）**
原型 `rgb(7,139,97)` ↔ 现状 `rgb(5,150,105)`，出现在分页当前页、当前页签、新建按钮底色。

**G7 状态标签形状（5~6 单元）**
`border-radius 11px→999px`（胶囊 vs 半圆）、现状多一圈 `border-width 0→1px`、底色不同。

**G8 弹层投影深浅（5 单元，靠新增 box-shadow 采集才查出）**
抽屉/弹窗：原型 `rgba(27,48,39,0.16) 0 16px 42px` → 现状 `rgba(15,15,15,0.14) 0 8px 28px`，**现状投影明显更浅更收**。

**G9 工具栏留白（6 单元）**：`padding-top/bottom 17px→0`。
**G10 内容层外边距（7 单元）**：现状比原型多包的 `.list-page` 那层没继承 `margin-top 28px→0`。

## 四、结构性差异（非样式，需负责人确认）

1. **连接器·业务系统页签**：原型无分页控件，现状有 `.list-pager`。对照 2026-09-08「全站统一分页控件」拍板，**现状多半是对的**，留待确认，工具不替人抹掉。
2. **用户技能审核页**：原型无分页区（现状有），同上。
3. **原型侧死链/未实现**（如实记录，未硬凑）：岗位「＋新建岗位」、岗位管理「修改绑定」、字段字典「✎编辑」三处按钮点了 DOM 无变化；岗位管理「岗位申请审批」页签未接实现。

## 五、豁免清单验证结果（本次扫描的附带目的）

| 豁免 | 全站命中 | 结论 |
|---|---|---|
| T1 表格密度 | 49 | 有效 |
| **T2 抽屉 body padding** | **5** | **有效**（上一轮 0 命中属「该扩配置」而非「该删豁免」，已证实） |
| T3 无对应令牌的原型值 | 140 | 有效 |

**T2 适用范围经实测收窄并已改注释**：原标题易被读成「全站抽屉都差这一档」，实际是原型里抽屉壳不止一种——专家/知识库两类壳是 `20/24/30`（与站内不同，本豁免要挡的就是它们）；角色/用户技能审核/审核中心/我的申请四处原型本就是 `22/28/34/28`，**与站内共享 DrawerEditor 完全一致、零差异**。反向验证：「用户·新建弹窗」是弹窗不是抽屉，T2 在该单元 0 命中，说明作用域判定准确未放大。

## 六、本轮修掉的工具缺陷（比业务差异更值得记）

扫描过程中两路共修 **7 类工具问题**，其中 **2 类是漏报**（工具说「无差异」但实际有差异，性质比多报严重）：

1. **【漏报】`box-shadow` 未采集**：Element Plus 输入控件的描边是 `box-shadow: inset` 画的，`border-width` 两侧都读作 0 —— 不采这项，**全站所有输入框/下拉的描边差异工具一律报「无差异」**。补采后新查出 4 类真差异（含 G8 弹层投影）。
2. **【漏报】降噪规则 (e) 不分轴**：「横向外框一致 ⇒ padding/margin 降级为噪声」这条规则（主流程上一轮加的）没分轴，把抽屉纵向内距的真差异整条吞掉——**恰恰是 T2 登记在案的那一条**，导致 T2 那轮「命中 4 条」全是被误扫进来的按钮内距，正主反而没进表，豁免自证机制因此失真。已改为分轴判定。
3. **豁免 T2 判定条件过宽**：`/drawer/i` 扫整串选择器，底栏按钮沾上 "drawer" 即被整片豁免——**看着有效、实际拦错东西，还顺手藏了一条真差异**。已收窄到正文区那一层本身。
4. **根容器自身永远「未命中」**：`root.querySelectorAll()` 只找后代找不到 root 本人，而「页面根」正是留白/限宽差异最爱出没处。已加 `root.matches()` 兜底。
5. **root 两侧错层 → 整张表 x 恒偏移**：列表页原型 root 取 `.page`、现状取层级更深的 `.list-page`，每个容器 x 恒差 34px；抽屉更甚，恒差 820px（整张表全是假差异）。已统一取同层元素。
6. **输入控件选错层，一次伪造 5 类「跨 6~8 单元的系统性差异」**：两侧真正画框的元素都在内层（`__wrapper` / `input.input`），错层比对齐刷刷报出 border/radius/背景/内距差异，**极像系统性真差异实则选错层**（与 td/.cell 同源）。
7. **EP 弹窗遮罩 `width=0`** 被判为不可见导致跑挂，改取弹窗本人。

> 这 7 类的共同教训：**工具报出来的「系统性差异」必须先证伪一遍**——错层与漏采都会伪造出极像真问题的成片差异。已全部写进代码注释与 README。

## 七、下一步建议（待负责人定）

按「改一处全站受益」的顺序，建议分批推进，每批闭环回归 + 复跑账本看条数下降：

- **批 1（收益最大、风险可控）**：G3 表格描边与行底色、G5 文字色令牌、G6 品牌绿 —— 都是令牌层改动，一处生效全站，且不改结构。
- **批 2**：G2 输入控件描边画法、G7 状态标签、G8 弹层投影 —— 涉及 Element Plus 覆盖层，需双主题逐一验。
- **批 3（争议项）**：G1 按钮体系 —— 条数最多（约 130），但改的是全站按钮观感，且 T3 已裁决「EP 按钮尺寸圆角与品牌绿维持站内规范」，**与本组部分重叠，需负责人先明确 G1 是否推翻 T3 裁决**。
- **批 4**：G4 分页、G9/G10 留白外距。
- **结构性差异**（第四节）与**原型死链**：非样式问题，建议单独确认，不混入修复批次。
