## 先讲两个基本概念（后文一直会用）

- **Node（节点）**：就是一台干活的机器（物理服务器或云主机）。集群 = 一群机器。
- **Pod**：应用真正跑起来的那个「工位」。K8s 把程序装进 Pod 里，再决定这个工位安排在哪台机器上。一台机器上通常同时跑着很多 Pod。

管理系统要管的，就是这两样东西：机器（Node）和工位（Pod）。

## 一、对「机器（Node）」能做哪些管理

一句话总结：**能看的信息非常多，能改的东西其实很少**——K8s 有意把机器设计成「多看少动」，日常管理主要就是下面 5 个动作。

### 1.1 能做的操作

| 管理动作 | 大白话解释 | 什么时候用 |
| --- | --- | --- |
| 暂停接新活 / 恢复接活（术语叫 cordon / uncordon，改 `spec.unschedulable`） | 给这台机器挂一块「暂停营业」的牌子：已经在上面干活的 Pod 不动，但新的 Pod 不会再安排进来 | 机器要维护、升级前的第一步 |
| 设置门禁（术语叫污点 taints） | 给机器加一道门禁规则，只有持「通行证」的 Pod 才能进来。门禁有三档力度：不收新人 / 尽量不收新人 / 连已经在里面的也请出去 | 把贵重机器（如带 GPU 的）留给特定任务；隔离出问题的机器 |
| 打标签（labels/annotations） | 给机器贴分类标签，比如「机房A」「高配机型」「测试环境」，之后安排 Pod 时可以按标签挑机器 | 机器分组管理，管理系统里最高频的写操作 |
| 清场（术语叫 drain） | 「暂停接新活 + 把上面的 Pod 一个个礼貌请走」的组合动作。注意：**K8s 没有现成的一键清场接口**，需要管理系统自己把这套流程编排出来（包括：不能把同一个服务的所有副本同时请走、系统守护类 Pod 要豁免、请不走怎么办等细节） | 机器下线、大修前的标准流程；也是节点管理里工作量最大、最能体现产品价值的功能 |
| 从集群移除（DELETE） | 把这台机器从集群名单里划掉（机器本身还得另行回收）。注意机器上的管家程序若还活着，会自己重新登记回来 | 机器报废、缩容 |

**不建议开放给管理界面的**：机器的内网网段分配、云厂商编号这类字段——它们由系统自动填写，人为改动只会出事。

### 1.2 能看的信息（监控展示面）

| 展示项 | 大白话解释 |
| --- | --- |
| 机器列表 + 实时刷新 | 建议用「订阅推送」方式（术语 watch）拿实时变化，而不是每隔几秒查一遍 |
| 健康红绿灯（status.conditions） | 每台机器自带 5 项体检指标：整体是否就绪、内存是否吃紧、磁盘是否吃紧、进程数是否吃紧、网络是否正常。这是管理系统首屏该放的东西 |
| 资源水位（capacity / allocatable） | 「机器总共有多少资源」和「刨去系统自用后还能分配多少」两个数，用来展示 CPU/内存/工位数的占用水位 |
| 机器档案（nodeInfo） | 操作系统、内核版本、K8s 管家程序版本、容器引擎版本等——做版本一致性检查和升级管理用 |
| 其他 | 机器的 IP 和主机名；本机缓存了哪些程序镜像；挂了哪些磁盘；还可以借官方通道直接读这台机器的实时性能数据（`nodes/{name}/proxy` 接口） |

## 二、对「工位（Pod）」能做哪些管理

一句话总结：**Pod 一旦创建，配置基本不能改**——想改配置等于拆掉重建。所以对 Pod 的管理不是「编辑」，而是四类动作：开/关、少量微调、排障诊断、看状态。

### 2.1 开与关（生命周期）

| 管理动作 | 大白话解释 |
| --- | --- |
| 创建 | 管理系统一般不直接手工建 Pod，而是建「管理者对象」（如 Deployment）让它代管；手工建 Pod 只用于调试 |
| 删除 / 重启 | K8s 里没有「重启 Pod」按钮——所谓重启就是删掉它，让管理者自动补一个新的。对卡死的 Pod 可以「强制删除」（不等它善后） |
| 批量删除 | 按标签一次删一批 |
| 礼貌请离（术语 eviction，独立接口） | 和直接删除的区别：它会先看「服务中断保护规则」——比如某服务只剩 2 个副本、规则要求至少留 1 个，那第二个请离请求会被拒绝。**给机器清场时必须用这个，不能用直接删除**，否则可能把一个服务全打没 |

### 2.2 能改的少数几样（微调）

- 标签/备注：随时可改。经典用法：改一下标签让某个 Pod 暂时脱离线上流量，单独排查问题；
- 换程序版本（容器镜像）：可以改，但托管 Pod 应该去改它的管理者模板；
- 原地调资源（`/resize` 接口）：不重启就调大调小 CPU/内存额度（较新版本才默认支持）；
- 注入临时排障工具箱（`/ephemeralcontainers` 接口）：对精简到连命令行都没有的 Pod，塞一个带工具的临时容器进去查问题；只能加不能撤。
- **其余全都不能改**：跑在哪台机器、挂哪些盘、环境变量、安全设置……都是出生即定，想改只能删了重建。

### 2.3 排障诊断（管理系统的价值高地）

| 功能 | 大白话解释 |
| --- | --- |
| 看日志（`/log`） | 支持实时滚动、只看最近 N 行、**看崩溃前上一次的日志**（排查反复重启问题的关键）等 |
| 网页终端（`/exec`） | 在浏览器里直接进入容器敲命令。**高危权限**：等于把这个容器的钥匙给出去了，权限要单独控制 |
| 端口临时直连（`/portforward`） | 把 Pod 内部的服务端口临时接到管理员本地，调试内部服务用 |
| 网页直访（`/proxy`） | 直接以网页请求方式访问 Pod 里的接口（比如健康检查页） |

### 2.4 能看的状态

- 生命阶段（等待安排 → 运行中 → 成功/失败）+ 四步就绪进度（已安排机器 → 初始化完成 → 容器就绪 → 可接流量），适合做成进度条；
- 每个容器的**重启次数**（核心告警指标）和上次挂掉的原因（比如「内存超限被杀」）；
- Pod 的 IP、所在机器、资源保障等级、启动时间；
- **务必配套查「事件记录」（Events）**：安排不上机器、镜像拉不下来、健康检查不过——这些「为什么出问题」的答案都在事件里，只看状态字段查不出原因。

### 2.5 管理系统落地建议

1. 功能按「查看 / 调度管控 / 开关 / 诊断」四组组织，权限也按这个分级（网页终端为高危，单独审批）；
2. 列表实时性用订阅推送（watch），不要轮询；
3. 「清场」流程自己编排，是最有价值也最费工的一块。

## 三、创建 Pod 时可以设置哪些「限制」

创建 Pod 就像给员工安排工位，能提的要求分五类。

### 3.1 资源额度（最核心）

- **「订多少」（requests）**：向系统申报「我大概要用 1 核 2G」。系统按这个数字帮你**挑一台放得下的机器**，也按它决定资源竞争时谁多分点；
- **「封顶多少」（limits）**：硬上限。超了会怎样，CPU 和内存待遇不同——
  - CPU 超限：**被限速**，程序变慢但不死；
  - 内存超限：**直接被杀掉重启**（术语 OOMKill）。生产上「Pod 反复重启」最常见的原因就是它；
  - 临时磁盘超限：整个 Pod 被赶出机器。防止日志写满拖垮整台机器；
- **保障等级（QoS，由上面两个数的填法自动决定）**：订多少=封顶多少 → 金牌（资源紧张时最后被牺牲）；填了但不相等 → 银牌；啥都不填 → 无保障（第一个被牺牲）。**所以「要不要认真填资源数字」的真实答案是：填法决定了你的 Pod 在资源紧张时的生死顺序**；
- 特殊装备：如申请 GPU（`nvidia.com/gpu`），GPU 不许超卖，订多少必须等于封顶多少。

### 3.2 位置要求（限制「能安排在哪台机器」）

| 参数 | 大白话解释 |
| --- | --- |
| 按标签挑机器（nodeSelector / nodeAffinity） | 「只去贴了 SSD 标签的机器」；高级版还能表达「最好去、去不了也行」的软性偏好 |
| 和谁在一起/不在一起（podAffinity / **podAntiAffinity**） | 最常用的是「反着来」：强制同一服务的几个副本**分散到不同机器**，防止一台机器挂掉全军覆没 |
| 门禁通行证（tolerations） | 声明「我能进有门禁的机器」。注意只是「允许进」，不是「必须去」 |
| 打散规则（topologySpreadConstraints） | 更精细地控制副本在机房/可用区之间的分布均匀度 |
| 钉死某台机器（nodeName） | 跳过智能调度直接指定机器，仅调试用，生产别开放 |
| 先审后调（schedulingGates） | 创建后先挂起不安排机器，等外部系统（比如审批流）放行了再调度 |
| 优先级（priorityClassName） | 资源不够时，高优先级的 Pod 可以把低优先级的挤走 |

### 3.3 时间限制

- **最长存活时间（activeDeadlineSeconds）**：注意语义是「这个 Pod 从启动起总共能活多久」，到点整个 Pod 判定失败。适合给一次性任务设「最多跑多久」；
- **优雅退出窗口（terminationGracePeriodSeconds，默认 30 秒）**：删除时先通知程序「你要被关了，把手头的活收个尾」，超时才强杀；
- 重启策略：挂了要不要自动拉起（服务类选「总是」，任务类选「失败才拉」或「不拉」）；
- 健康检查阈值：不健康 → 重启；没准备好 → 摘掉流量；慢启动应用给宽限期。阈值设太紧会误杀、造成流量抖动。

### 3.4 安全限制

一组「把容器关进笼子」的开关，管理系统应给一套安全默认值而不是让用户裸填：

- 禁止用管理员身份（root）运行；文件系统设为只读（被入侵也写不进恶意文件）；禁止提权；内核权限全关再按需开；禁「特权容器」（特权容器约等于直接拿到整台机器的钥匙）；
- 不共享宿主机的网络/进程空间（共享 = 打破隔离）；
- 用不到集群管理接口的业务 Pod，不要自动配发访问令牌（缩小被攻击面）。

### 3.5 集群侧的三道关卡（不在 Pod 参数里，但决定创建能否成功）

用户提交的创建请求，最终还要过管理员预设的三道关：

1. **默认值与上下限（LimitRange）**：没填资源数字的自动补默认值，填得离谱的直接拒绝；
2. **部门总额度（ResourceQuota）**：整个空间的资源总池子，用光了就不许再建。⚠️ 常见坑：设了总额度的空间里，**不填资源数字的 Pod 会被直接拒绝**；
3. **安全等级准入（Pod Security Admission）**：给空间定安全级别，不达标的 Pod（比如要特权）进门就被拦。

管理系统要做的：表单把资源数字设为必填并给默认值，提交被拒时把这三道关的拒绝原因翻译成人话展示。

## 四、「运行规格」页面（/admin/runtime-specs）可行性分析

对照页面全部管理项逐一核验。结论：**页面现有功能全部能实现；约一半由 K8s 直接承担，另一半靠我们自己的后端（平台侧）实现。**

> **已修改（2026-09-03 负责人三点拍板）**：原结论为「11 项全部可实现，其中出网有前提、任务超时有语义冲突待拍板」。现按拍板修订为：① **出网配置项取消**（页面与 mock 已同步移除，现存 10 项）；② **任务超时定性为业务概念**——调用方发起任务后开始计时，N 分钟内没拿到结果就主动结束该任务，由平台侧实现，与 K8s 参数无关；③ **运行模型定为用户级常驻 Pod**，当前做不到任务级 Pod。原分析过程保留在 4.2 / 4.4 供追溯。

### 4.1 K8s 直接就能干的（5 项）

| 页面项 | 怎么实现 | 结论 |
| --- | --- | --- |
| CPU（核） | 就是资源额度里的 CPU 订量+封顶（requests/limits.cpu） | ✅ |
| 内存（Gi） | 内存订量+封顶；超了会被杀重启（limits.memory） | ✅ |
| 临时磁盘（Gi） | 临时盘封顶；超了整个 Pod 被赶走（limits.ephemeral-storage） | ✅ |
| 「订量=封顶」的 demo 设定 | 恰好构成金牌保障等级（Guaranteed QoS）——资源紧张时最后被牺牲，给每个用户的专属 Pod 稳定体验 | ✅ 这个设计选择在 K8s 里说得通，是加分项 |
| 删除提示「已运行实例不受影响」 | 规格只是建 Pod 时用的模板，删模板不影响已经跑起来的 Pod | ✅ 与 K8s 行为一致 |

### 4.2 曾标注「有前提/有坑」的 2 项（均已有定论）

**① 出网=禁止（egress DENY）——「已修改」：该配置项于 2026-09-03 拍板取消**，页面表单、列表列与 mock 数据已同步移除（原「高敏离网」示例规格随之改名「高敏」，去掉断外网表述）。
原结论保留作参考（若未来恢复此功能仍然成立）：断外网不是 Pod 身上的开关，而要另外配一条防火墙规则（NetworkPolicy）；且有两个前提——网络插件必须支持（Calico/Cilium 可，老式 Flannel **不支持且不报错**，安全功能最怕这种静默失效）；「断外网但内部可访问」还需放行内部网段和域名解析。

**② 任务超时（timeoutMin）——「已修改」：2026-09-03 拍板定性为业务概念**，与 K8s 参数无关：调用方发起任务后就开始计时，N 分钟内没拿到结果，就由平台主动结束该任务。抽屉提示语与 mock 注释已按此口径修正。
原结论保留作参考：此前代码注释把它对应到 K8s 的「最长存活时间」（activeDeadlineSeconds），但那个参数管的是「Pod 从启动起总共能活多久」，与「每个用户一个常驻 Pod、连续服务多次任务」的模型对不上——给常驻 Pod 设 3 分钟存活，它会启动 3 分钟后整个死掉，而不是「每次任务最多 3 分钟」。该冲突正是本次拍板解决的问题。

### 4.3 K8s 没有、必须我们自己后端实现的（4 项）

| 页面项 | 为什么 K8s 没有 | 怎么实现 |
| --- | --- | --- |
| 空闲回收（idleRecycleMin） | K8s 不知道「业务上闲没闲」，Pod 不会因为没活干就自动消失 | 后端做个回收器：记录每个用户 Pod 最后一次干活的时间，闲够了就删掉。常规做法，可行 |
| 并发上限（concurrency） | 「一个 Pod 同时接几个任务」是应用层的事，K8s 没这个概念 | 后端任务队列限流。可行 |
| 使用需审批 + 审批状态 | 纯业务流程 | 后端审批流。可以优雅结合 K8s 的「先审后调」机制（schedulingGates）：审批没过，Pod 先挂起不启动 |
| 规格模板的增删改查、重名校验、用户绑定、汇总统计 | K8s 没有「规格模板」这种对象 | 后端数据库存模板，建 Pod 时展开成具体参数。可行 |

另：「能力边界说明」里「可处理 20MB 以内文件」这类话，是给 FDE 看的**人话翻译**，本来就不需要也无法由 K8s 强制执行——页面现有定位（D17 口径）是对的。

### 4.4 运行模型（已裁决）

**「已修改」：原为待拍板差异，2026-09-03 负责人裁决采用 A 方案——用户级常驻 Pod**（每个用户一个 Pod，连续服务多次任务；当前做不到任务级 Pod）。随之确定：

- 任务超时 = 业务概念，调用方计时、超时主动结束任务（见 4.2 ②）；「空闲回收」字段保留且成立；
- K8s 的「最长存活时间」（activeDeadlineSeconds）在本模型下不使用。

原待拍板记录保留作参考：当时的矛盾是 mock 注释把任务超时对应到 activeDeadlineSeconds（隐含 B 方案「每任务一个 Pod」），却又同时保留只在 A 方案下有意义的「空闲回收」字段——两个模型各自都能实现，但不能混用。本次裁决消除了该矛盾。
