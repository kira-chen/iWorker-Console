## 一、现状诊断：问题出在哪

`docs/` 现在有 11 个目录 + 2 个散文件，是 09-03 到 09-16 一路「原型退役 → PRD 一致性整改 → 测试审计 → 新模块」几场战役各自留下的。逐个看过后，问题归结为四条：

## 二、先分类：docs/ 里的文档只有四种

按「会不会结束」把所有文档分四类，生命周期规则跟着类型走，而不是跟着目录走：

| 类型 | 特征 | 例子 | 会不会归档 |
|---|---|---|---|
| **A 正本** | 长期有效、只有「最新版」有意义，改就直接改 | `PRD/`、CLAUDE.md、README | 不归档，git 历史即版本 |
| **B 规范** | 长期有效的约束或参考，偶尔更新 | UI 规范图、接口规范、本方案定稿后的「文档管理规则」 | 不归档；被替代时整份删除并在替代者里注明 |
| **C 台账** | 按时间只增不改的流水，价值在「可回溯」 | `PRD-review/YYYY-MM-DD.md` | **有保质期**（2026-09-17 负责人改口径）：一份日记录里的决策一旦上升到 CLAUDE.md / PRD / 技能、待办一旦转到待决策清单或销项，即「已被吸收」，可归档到本机；仓库只留仍含未吸收内容的记录 |
| **D 工作项** | **为一件事而生，这件事结束它就结束** | 改动记录、一致性审查结果、待决策清单、补定义清单、测试审计报告、调研/方案稿、复盘 | **归档**：这是唯一有生命周期的类型 |

绝大多数文档是 D 类。D 类才需要下面的状态机。

## 三、D 类工作项的生命周期

### 3.1 三个状态

```
进行中 ──(最后一条待办销项)──▶ 已闭环 ──(同一次 commit 内 git mv)──▶ 已归档
```

- **进行中**：文件里还有至少一条「待确认 / 待决策 / 待补 / 待销项」没结。
- **已闭环**：所有条目都有结论（做了 / 不做 / 转记到别处），文件头打上 `已闭环` 戳。
- **已归档**：物理搬进 `docs/归档/`，原路径不再存在。**归档 = 闭环的自动后果，不是另一个需要拍板的动作。**

### 3.2 每份工作项文档的文件头（强制）

```markdown
> 状态：进行中 | 已闭环（YYYY-MM-DD） | 已归档（YYYY-MM-DD）
> 责任人：<谁负责把它推到闭环>
> 闭环条件：<一句话说清「什么算完」>
> 关联：<触发它的 PRD 修订 / commit / 上游文档>
```

「闭环条件」是关键：写文档的人当场就要说清楚这份文档什么时候算完。写不出来的，说明它不是工作项，该并进台账或规范里。

### 3.3 各类工作项的默认闭环条件

| 工作项 | 产出者 | 默认闭环条件 |
|---|---|---|
| PRD 改动记录（现 01-） | `/prd-import` | 末尾「待确认清单」全部销项 |
| 一致性审查结果（现 02-） | `/prd-import` | 所有 Q 条目标【已解决】或转入待决策清单 |
| 待决策清单（现 03-） | 团队整理 | 每条有负责人批注 **且已落地**（只批注未落地不算） |
| 补定义需求清单（现 04-） | 团队整理 | 每项要么 PRD 已补写、要么负责人裁「不做」 |
| 测试审计报告 + 待决策（现 05-） | `/test-audit` | 处置清单执行完、J 项全部裁决；**报告本身在下一轮审计开始时归档**（它记着下一轮的起点 commit） |
| 调研 / 方案稿（调研讨论/） | 任何人 | 结论被采纳进 PRD / 代码 / 规则，或明确放弃；**被采纳的要在文件头写「去向」** |
| 复盘 | 战役结束时 | 写完即闭环，**但不归档**（复盘是给后人看的，放归档里就没人看了；单独留在 `复盘/`） |

### 3.4 谁来归档、什么时候

- **销掉最后一条待办的人负责归档**，在同一次 commit 里 `git mv` 过去（git 保留历史，`git log --follow` 可追）。
- 兜底：每次「阶段推送」前（CLAUDE.md 已有这个节点），推送者扫一遍工作区，把状态已是「已闭环」但还没搬的一并搬走。
- 归档时只做两件事：改文件头状态行、`git mv`。**不改正文、不加失效声明**——状态行已经说明一切，改正文反而破坏「当时是怎么说的」。

### 3.5 归档去哪

**负责人拍板（2026-09-17）：沿用 09-10 口径，归档放负责人本机仓库根 `Archive/docs-归档/`（.gitignore，不入库）**，目录结构镜像工作区（`Archive/docs-归档/02-…/xxx.md`）。

据此 3.4 的动作改为：闭环者在文件头打「已闭环」戳并 commit；**搬出仓库的动作只由负责人做**（`git rm` + 本机 Archive/ 收），其他合作者不动。合作者要查已归档文档时走 `git log --follow -- <原路径>` / `git show`，或向负责人索取。

> 曾提的替代方案（`docs/归档/` 入库，便于多人查阅）未采纳，理由留此备查：负责人倾向仓库只保留活文档。

## 四、目录结构建议

原则：**目录按类型分，不按战役分**；工作项目录名去掉「原型」字样；解决编号撞车。

```
docs/
├── PRD/                     A 正本（不动）
├── 规范/                    B 规范：UI/、接口/、文档管理规则.md（本稿定稿后的正式版）
├── PRD-review/              C 台账（不动，只增）
├── 01-PRD改动记录/          D 工作区（原 01-PRD改动记录）
├── 02-PRD与代码一致性审查/  D 工作区（原 02-PRD与代码一致性审查）
├── 03-待决策清单/           D 工作区（原 03-待决策清单；测试审计的待决策也归这里）
├── 04-待补需求定义/         D 工作区（原 04-待补需求定义）
├── 05-测试用例审计/         D 工作区（不变）
├── 调研讨论/                D 工作区（不变）
├── 复盘/                    D 但不归档（不变）
├── 归档/                    已闭环工作项，镜像上面 01–05 + 调研讨论
└── README.md                一页纸：目录说明 + 生命周期规则 + 「当前进行中」索引
```

改名影响面（拍板后一并改，不另起事）：CLAUDE.md「docs/ 工作目录」段、`.claude/skills/prd-import/SKILL.md`、`.claude/skills/test-audit/SKILL.md` 与其 `视角与操作清单.md`、`daily-update-log/SKILL.md`（顺手删掉对 `docs/update/`、`docs/API迭代需求/` 的引用）、README。docs 内部文档互相引用的路径用 `grep` 全量替换。
