### 给提交者的解决方案（逐条）

**第 0 条（最根本）：每次 `git push` 之前，在本地跑完这两条且都绿，再推。**

```bash
cd frontend
npm run test    # vitest，约 2200 条，1 分钟左右
npm run build
```

本地红就不要推。推上去只是把同一个红搬到 GitHub 多等 5 分钟，还占用他人的 CI 额度和注意力。这条在 `CLAUDE.md` 里早就是「commit 前全量测试 + 构建须绿」，CI 只是兜底，不是替代。PR #9 的 81 条本地一跑就能全部看到。

**第 1 条：页面新加 `useRoute` / `useRouter` 依赖时，把所有挂载该页面的测试里的 `vi.mock('vue-router', ...)` 一起补全。**

这一条解释了 81 条里的 63 条（43 + 20）：一个页面级依赖缺失会让整个测试文件从第一条开始全崩，看起来吓人，其实是一处一行的改动。做法：改完页面后 `grep -rl "该页面文件名" src/**/__tests__/`，每个命中的测试文件里给 mock 补 `useRoute: () => ({ query: {} })`。PR #8 的 `6804ad6` / `bc74335` 已经这样修了，方向正确。

**第 2 条：给数据模型加新字段（尤其是必填字段）时，同步补测试 fixture 和表单填值。**

- 连接器加 `type`：所有构造连接器 fixture 的测试都要补上（`6804ad6` 已修）。
- 专家编辑器加「专家类型」必填：测试提交前要先给这个字段赋值，否则校验拦住、断言永远等不到提交（`b3bd2c1` 已修）。
- 判据很简单：**你把哪条用例跑红了，那条就归你改**，不需要研究整个测试体系。

**第 3 条：改了 PRD 数值（字数上限等），把断言里的旧数值一并改掉。**

`217ce1f` 把描述类 200→2000、示例问题 60→300 时，对应断言里的 `max: 500`/`max: 60` 要一起改（`bc74335`、`d3914e2`、`c6ad613` 已修）。建议改数值前先 `grep -rn "max: 500" src/**/__tests__/` 把要改的位置列出来。

**第 4 条（需要改回来）：功能按需求删掉后，对应旧用例应当删除或改写，不要为了让用例变绿把废弃功能加回去。**

PR #8 的 `688ea7f`（commit 说明写的是「动态 import 改静态消除抖动」）实际做的是**把 `d4ff97d` 按新需求删掉的 `approve / reject / markRebound / list` 四个函数又加回了 `positionApplicationsMock.js`（+120 行）**，让 11 条旧用例通过。核对 main 现状：这四个函数**只有测试文件在 import，没有任何页面调用**——等于把 PRD 已废弃的「通过/驳回」逻辑当死代码留在 mock 层，还配了一套测试在守护它。

按工程大原则（代码是给研发看的参考实现），这是反方向的修法。**建议处理**：删掉这四个函数以及 `positionApplicationsMock.test.js` 里对应的 11 条用例，只保留「分配岗位」路径的用例；如果「已处理记录」列表页仍需要一个列表接口，按新语义重写并另起用例名。此项待提交者与负责人确认归属后执行，本轮未动。

**第 5 条：不要为了变绿 `skip` / 注释用例。** 用例红只有两种含义——用例过期（改用例）或代码改错（改代码），跳过等于拆掉报警器。

**第 6 条：commit 说明写实际做了什么。** `688ea7f` 的说明与 diff 内容不符，会误导后来人排查。
