## 工作项的生命周期

```text
进行中 ──(最后一条待办销项)──▶ 已闭环 ──(负责人搬出仓库)──▶ 已归档
```

- 每份工作项文件头四行（强制）：`状态 / 责任人 / 闭环条件 / 关联`。闭环条件写不出来的，不是工作项。
- 销掉最后一条待办的人，在同一次 commit 里把状态改「已闭环（日期）」。
- **归档只由负责人做**：`git rm` + 存本机 `Archive/docs-归档/<原目录名>/`（不入库）。合作者要查已归档文件：`git log --follow -- <原路径>` / `git show <commit>:<路径>`。
- 发现需要**别人**处理的事，不要写在自己的文档里等人看——追加到 `产品经理待办任务/<对方>.md`。**按模块分派**（09-17 负责人定）：01 总览、02 岗位、03 能力、05 治理、06 组织 → 浦月 `yuepu`；04 运行 → 曹春林 `clcao`。

## 调研讨论的三条铁规（2026-09-17 负责人定）

1. **有指令才开文档**：只有负责人明确说「就 X 建一个讨论点」才新建 `调研讨论/YYYY-MM-DD-主题.md`；执行任务时冒出的想法、顺手的分析，不得自行开一份——写进 commit message 或待办即可。
2. **过程性记录**：讨论中的重要内容都进文档——关键论据、方案取舍、被推翻的旧结论（保留原文并标「已修改：改成了什么」）、负责人的拍板原话。写完一轮就提交入 git，不攒。
3. **必须有结论才算闭环**：文末固定一段「## 结论」，写清**定了什么**、**去向是哪**（进 PRD 哪个 md / 代码哪个 commit / 规则哪一条 / 转成谁的待办，或明确「放弃」）。没有结论段 = 讨论未闭环，不得归档；有了结论且去向已落实，才打闭环戳、由负责人归档。

文件头四行照工作项规则：`状态 / 责任人 / 闭环条件 / 关联`，其中「闭环条件」默认就是「结论段写完且去向落实」。
